### root-cause
- [root-cause|high] ADR-039 user-project self-modification enforcement is dead scaffolding — `src/orchestra/self-modifying-detector.ts:237-243` — the only branch that returns `mode:'enforce'` lives inside `enforceSelfModifyingTask`, which has **zero production callers** (verified above). `self_mod_enforce: true` therefore never blocks anything; a user project task that writes to orchestration source patterns is never gated. The guarantee implied by the ADR ("enforce when opted-in") is structurally soft because no caller acts on the decision. — Exact softening line: the `enforce` result at 240-242 is computed but unreachable from any runtime path.
- [root-cause|medium] Docker health-check fails *open* on inspect error / malformed output — `src/orchestra/spawn-backend-docker.ts:946-950` (`if (inspect.status !== 0) ... return { healthy: true, ... }`) and `:952-956` (malformed parse ⇒ `{ healthy: true }`) — a container whose `docker inspect` errors or emits unexpected text is optimistically declared healthy and handed to `monitorContainer`, consuming no retry. The docstring acknowledges this ("fail-open"). — Trust-without-verify at the health gate: only the later `docker wait` catches a genuinely-dead container, so a real `container_start_failed` masked by inspect noise loses its `MAX_SPAWN_ATTEMPTS` retry.
- [root-cause|low] Unknown model silently degrades to the `claude` provider at spawn time — `src/orchestra/spawn-backend-docker.ts:555` (`const provider = modelRegistry.get(model)?.provider ?? 'claude';`) — an unregistered model id silently resolves to provider `'claude'`; since `getProviderCommandSpec('claude')` returns a valid spec, the honest-fail NO_GO path (lines 557-582) is bypassed and a claude container is spawned for a model the registry does not know. — Silent fallback can hide a model-registry/routing regression behind a "successful" claude spawn.

## Summary
This cluster is the spawn/security boundary of the orchestrator, and the audit shows the pattern is "machinery built, top-level wire missing." The most material gap is memory governance: `DockerSpawnBackend` fully implements per-kind and per-config memory limits, but `SpawnBackendFactoryOptions` + all four production `create()` call sites never forward them, so `worker_memory_limit`/`worker_memory_limit_by_kind` are inert and every container runs at the hardcoded 4g/6g default. The security/enforcement story is similarly soft: ADR-039's user-project self-mod enforcement (`enforceSelfModifyingTask`, including the `mode:'enforce'` branch) is dead code with zero callers, so `self_mod_enforce` has no runtime effect — consistent with deckent's documented advisory/soft posture (ADR-037 V1.0), but here the softness is *accidental* (no consumer) rather than an explicit gate. Smaller drift risks cluster around redaction (three same-named `redactSensitive` impls with no shared pattern source) and several superseded-but-still-exported helpers (`getProviderBinaryForModel`, `isTmuxAvailable`, `_internals`).
