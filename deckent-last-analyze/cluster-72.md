## Findings

### unwired (zero-caller, grep-verified)

- [unwired|high] `SandboxSpawnBackend` + `createSandboxBackend` have zero src consumers — `src/providers/sandbox.ts:28,156` — grep `SandboxSpawnBackend|createSandboxBackend|new SandboxSpawnBackend` over `src/` returns ONLY definitions inside `sandbox.ts`; no import elsewhere. The class docblock `* Activated with `--sandbox` flag on `deckent start`.` (`sandbox.ts:26`) is FALSE — `start.ts:160` defines `--sandbox-mode` = `'Run in sandbox mode (git stash + restore)'` (a `SandboxState` git-stash, unrelated to this backend). The entire memory-limit / scope-enforcement / network-block security layer is dead code never reached in production.
- [unwired|low] `createSubprocessBackend()` factory is never called in src — `src/providers/subprocess.ts:334` — grep shows production builds the backend via `new SubprocessSpawnBackend(...)` directly (`claude.ts:107`, `orchestra/spawn-backend.ts:190,195`); the exported factory has no src caller (test-only), a parallel-but-unused construction path.
- [unwired|medium] `OllamaAdapter.getModelForTier()` has no call-site — `src/providers/ollama.ts:572` — grep `\.getModelForTier\(` over `src/` matches only `@deprecated` doc comments (`gemini.ts:70`, `codex.ts:40` "use adapter.getModelForTier() instead") and the three adapter definitions; no actual invocation. Tier→model resolution here (and on codex/gemini) is defined but unconsumed.

### dormant (defined-but-unread / no-op gate)

- [dormant|high] `SandboxSpawnBackend.buildEnv()` is never invoked — `src/providers/sandbox.ts:103` — grep `\.buildEnv\(` over `src/` returns no call-site. `spawn()` (`sandbox.ts:46-61`) only calls `super.spawn(...)`, and `SubprocessSpawnBackend.spawn` builds its own `env` (`subprocess.ts:154-158`) without ever calling `buildEnv`. Therefore `memoryLimitMb` (`sandbox.ts:37`) and `blockNetwork` (`sandbox.ts:41`) are computed into an env object that nothing applies — the `--max-old-space-size` cap and proxy network-block are inert.
- [dormant|medium] `providers/ollama.ts` `complete()` / `stream()` have no in-tree adapter consumer — `src/providers/ollama.ts:443,476` — grep `\.complete(`/streaming call-sites resolve to unrelated code (`goal-planner.ts:87 input.complete(...)`) or to the *other* ollama adapter; the REPL streaming path imports `createOllamaAdapter` from `src/agent/provider-tooluse/ollama.js` (`native-transport.ts:15`), not this file. The registry-built adapter (`core/provider.ts:838`) drives the spawn path, leaving these HTTP methods defined-but-unread here.
- [dormant|low] `OpenAICompatibleAdapter.buildCommand()` returns a comment placeholder, not a command — `src/providers/openai-compatible.ts:201-203` — `return `# ${this.name} HTTP adapter — POST ${this.baseURL}/chat/completions ...``; a no-op gate for the `ProviderAdapter` shape (HTTP adapters have no spawn/dry-run command), never producing an executable string.

### inconsistent (conflicting default / duplicate / divergent)

- [inconsistent|medium] Two different `createOllamaAdapter` factories with divergent signatures — `src/providers/ollama.ts:708` vs `src/agent/provider-tooluse/ollama.ts:15` — this file's `createOllamaAdapter(projectDir, opts)` (spawn/HTTP adapter) collides by name with `createOllamaAdapter(opts: OllamaAdapterOptions)` (REPL tool-use). `doctor.ts:457` + `core/provider.ts:839` import the former; `native-transport.ts:62` imports the latter. Same export name, different files, different shapes — a maintenance trap.
- [inconsistent|medium] `isAvailable()` and `detect().available` disagree on "available" — `src/providers/ollama.ts:323-330` vs `:381` — `isAvailable()` returns `res.ok` (server reachable) while `detect()` sets `available: models.length > 0`. A reachable Ollama server with zero pulled models yields `isAvailable()===true` but `detect().available===false`; routing keyed off `isAvailable` can select Ollama then find no usable model.
- [inconsistent|medium] `buildCommand()` dry-run string does not match what `spawn()` actually runs — `src/providers/ollama.ts:532-539` vs `:272-276` — `buildCommand` returns a `curl ... /api/generate` string, but `spawn()` launches `node [workerEntryPath, taskId, apiId, host]` (the agentic worker entry, T-233-002). The displayed/dry-run command diverges from the real execution.
- [inconsistent|medium] Sibling backends have divergent heartbeat lifecycles — `src/providers/ollama.ts:279,676` vs `src/providers/subprocess.ts:172,287` — `SubprocessSpawnBackend.spawn` installs a 15s `setInterval` refresh + increments `hbSequence` (`subprocess.ts:171-175`); `OllamaAdapter.spawn` writes the heartbeat exactly once at spawn (`ollama.ts:279`) with a fixed `sequence: 0` (`ollama.ts:686`) and never refreshes it. Same contract, two behaviors.
- [inconsistent|low] `enforceScope` path normalization mismatches its own `allowedDirs` — `src/providers/sandbox.ts:38-40,89-90,148` — `allowedDirs` are stored via `resolve(d)` (`:39`) but the checked dir is `realpathSync`'d when it exists (`safeResolve`, `:148`). If an allowed dir is itself a symlink, `realpath(dir).startsWith(resolve(allowedDir)+'/')` fails for a legitimately-inside path (or vice-versa) — asymmetric resolution.

### dead-test (skip / tautological / mock-only)

- [dead-test|medium] `buildEnv()` is fully unit-tested but never called in production — `tests/providers/sandbox.test.ts:206-259` — the `describe('buildEnv()')` block asserts `NODE_OPTIONS` contains `--max-old-space-size=256/512` etc., giving green-CI confidence that the memory cap works; yet `buildEnv` has zero production call-site (see dormant finding) and no test asserts `spawn()` applies that env. Classic tests-pass-feature-dead.
- [dead-test|low] Entire `SandboxSpawnBackend` suite exercises an unwired class via mocked spawn — `tests/providers/sandbox.test.ts:18-20,87` — `vi.mock('node:child_process', () => ({ spawn: vi.fn() }))` + mock `node:fs`; coverage accrues to a backend never instantiated in the live system, so suite-green ≠ shipped-behavior.

### root-cause (advisory-soft / trust-without-verify / silent-fallback / hardcoded-0-metric)

- [root-cause|high] Sandbox memory-limit is structurally non-functional (trust-without-verify wiring) — `src/providers/sandbox.ts:58-60` — comment: `// NOTE: NODE_OPTIONS memory limit is injected via buildEnv(), called by // consumers before spawning (e.g., start.ts --sandbox-mode).` This delegates enforcement to a "consumer" that does not exist (no `buildEnv` caller; `--sandbox-mode` is git-stash). The advertised resource cap silently does nothing.
- [root-cause|medium] Subprocess fallback result trusts exit code as test outcome — `src/providers/subprocess.ts:217-218` — `testsPassed: code === 0,` / `selfAssessment: code === 0 ? 'GO_WITH_TECH_DEBT' : 'NO_GO',`. When a worker exits 0 without writing a `.result`, the backend fabricates `testsPassed:true` purely from the exit code — no verification that tests ran or passed; a silently-crashed-but-exit-0 worker is recorded as a partial success.
- [root-cause|medium] Heartbeat `filesChangedCount` is hardcoded 0 on both backends — `src/providers/subprocess.ts:295` + `src/providers/ollama.ts:685` — `filesChangedCount: 0,` is written verbatim every heartbeat; the dashboard/auditor metric for files-changed is always 0 for subprocess and ollama workers regardless of actual edits (hardcoded-0-metric).
- [root-cause|medium] Ollama heartbeat goes stale by construction → false auditor alert — `src/providers/ollama.ts:279,686` — written once at spawn with `sequence: 0` and never refreshed (no interval). Auditor stale-heartbeat detection (>2min) will flag every long-running Ollama worker as stale even when healthy.
- [root-cause|low] Silent model-id fallback bypasses the registry — `src/providers/ollama.ts:264,453,486,537,542` + `src/providers/subprocess.ts:60,75` — `modelRegistry.get(model)?.apiId ?? model`; an unknown model is forwarded as the raw alias string instead of failing fast, so a typo'd / unregistered model id is silently spawned (CLI/API will then reject it with a less-actionable error).
- [root-cause|low] `OllamaAdapter.getModelForTier` final fallback is a hardcoded literal — `src/providers/ollama.ts:583` — `return 'llama-3.2-3b';` after the tier walk; if the registry is reconfigured without that id the method returns a model that may not be installed/registered (silent default).
- [root-cause|low] `OpenAICompatibleAdapter.isAvailable()` claims availability from env presence only — `src/providers/openai-compatible.ts:159-161` — `return Boolean(process.env[this.apiKeyEnv]);` (and `diagnoseAvailability` hardcodes `binaryFound: true`, `:169`). A present-but-invalid/expired key reports "available"; no probe verifies the credential, so the failure surfaces only at first `send()`. (Documented as intentional cold-path behavior, `:156-158`.)
- [root-cause|low] Token usage defaults to 0 on partial upstream `usage` — `src/providers/openai-compatible.ts:143-144` — `inputTokens: json.usage.prompt_tokens ?? 0,` / `outputTokens: json.usage.completion_tokens ?? 0,`. An upstream that returns a `usage` object missing one counter records that dimension as 0, under-reporting cost metrics.

## Summary

- **Most material:** the **sandbox backend is entirely unwired** (`SandboxSpawnBackend`/`createSandboxBackend` zero src callers) and its core security feature (`buildEnv` memory-limit + network-block) is **dormant + structurally non-functional** — the class docblock and `spawn()` comment both claim a `--sandbox` activation/consumer that does not exist (`start.ts --sandbox-mode` is git-stash). Its tests (`sandbox.test.ts`) are mock-only and assert `buildEnv` behavior that nothing in production triggers → green CI masks dead security code.
- **Reliability/observability root-causes:** subprocess fallback infers `testsPassed` from exit code alone (`subprocess.ts:217-218`); `filesChangedCount` is hardcoded `0` on both backends; Ollama heartbeat is written once with `sequence:0` and never refreshed → guaranteed stale-heartbeat false-positives, diverging from subprocess's 15s-interval lifecycle.
- **Inconsistencies:** duplicate `createOllamaAdapter` export across two files with divergent signatures; Ollama `isAvailable()` (reachable) vs `detect().available` (models>0) disagreement; `buildCommand` curl-string vs real `node` worker-entry spawn; symlink-asymmetric `enforceScope` normalization.
- **Lower-severity root-causes:** silent `?? model` registry-bypass fallback (ollama+subprocess), hardcoded `'llama-3.2-3b'` tier fallback, env-presence-only `isAvailable` for OpenAI-compatible, and `?? 0` token-usage under-reporting.
- All findings are read-only observations; **no source was modified**. Caller/zero-caller claims grep-verified over `src/` (definitions and test files excluded from the "zero-caller" determination).
