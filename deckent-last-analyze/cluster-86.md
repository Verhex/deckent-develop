# mcp-client#1 — outgoing MCP-client (broker · config · registry · types)

Scope: `src/mcp-client/broker.ts`, `src/mcp-client/config.ts`, `src/mcp-client/registry.ts`, `src/mcp-client/types.ts`.
Method: full read of all 4 files + repo-grep of every exported symbol over `src/` (production) vs `tests/` (test-only). Code-only; no source changed.

Production consumers verified: `src/cli/commands/chat-mcp-bridge.ts` (`buildMcpBridge`), `src/cli/repl/mcp-bridge.ts` (`initReplMcpBridge`, default-OFF `mcp_client_enabled`), `src/cli/repl/run.tsx:189`, `src/cli/commands/chat-native.ts:620`, `src/cli/commands/mcp.ts` (`loadMcpServers`).

## Findings

- [unwired|med] Connection teardown never called in production (lifecycle leak) — `src/mcp-client/broker.ts:126,138` — `async disconnect(name)` + `async disconnectAll()`; grep `\.disconnect(`/`disconnectAll` over `src/` → **zero production callers** (`disconnect` self-called only by `disconnectAll` at `:141`; both invoked solely by `tests/mcp-client/broker.test.ts:72,93,102,142`). — `buildMcpBridge.loadAndConnectAll()` (chat-mcp-bridge.ts:223) opens broker connections but no production path ever calls `disconnect`/`disconnectAll`; REPL MCP connections live for the whole session with no cleanup on exit. Public teardown API exists but is unwired.

- [unwired|low] `broker.list()` has zero production callers — `src/mcp-client/broker.ts:79` — `list(): string[] { return Array.from(this.pool.keys()); }`; declared in the consumer's `BridgeBrokerLike` interface (`chat-mcp-bridge.ts:50 list(): string[]`) yet `buildMcpBridge` never invokes `broker.list()`. Only `tests/mcp-client/broker.test.ts:100,104` call it. — Listing of connected servers is surfaced via `registry.list()`, not the broker; the broker accessor is dead in production.

- [unwired|low] `registerConnection` is a test-only injection seam — `src/mcp-client/broker.ts:50` — `registerConnection(name, client, transport, def)`; grep over `src/` → no production caller; used only by `tests/mcp-client/broker.test.ts:65,79,99,129`. JSDoc self-declares "(in-memory tests)". — Intentional test seam, but ships as a public method with no production wiring; production always goes through `connect()`.

- [unwired|low] `registry.size` getter has zero production callers — `src/mcp-client/registry.ts:93` — `get size(): number { return this.entries.size; }`; grep `\.size` over `src/` finds only the definition; all reads are in `tests/mcp-client/mcp-registry.test.ts:53,57,69,77,80`. — Test-only metric; never consulted by the bridge/REPL.

- [dormant|med] `onCall` audit hook + `emitCall` are production-dormant (all constructions omit it) — `src/mcp-client/broker.ts:41,153-160` (+ `types.ts:49`) — `this.onCall = options.onCall;` / `private emitCall(record) { if (!this.onCall) return; … }`; all 3 production constructions pass no hook: `chat-native.ts:620 new McpClientBroker()`, `repl/mcp-bridge.ts:97 new McpClientBroker()`, `run.tsx:189 new McpClientBroker({})`. `createMcpAuditSink` (chat-mcp-bridge.ts:121) — the only thing that would build the hook — has **zero callers** (referenced only inside its own doc comments at chat-mcp-bridge.ts:17,114). — `repl/mcp-bridge.ts:28-30` documents the choice ("constructed WITHOUT an onCall hook … wiring onCall too would double-log"); the bridge audits via its own `writeEvent`. Net effect: broker.ts's onCall branch (and `emitCall`) execute only in `broker.test.ts`; the type comment that says Task 5 routes records "via onCall" is no longer the live path.

- [dormant|low] `clientName` / `clientVersion` options never set by any caller — `src/mcp-client/broker.ts:42-43` (+ `types.ts:50-51`) — `this.clientName = options.clientName ?? DEFAULT_CLIENT_NAME;` / `… ?? DEFAULT_CLIENT_VERSION;`; every production construction passes `{}`/nothing and no test sets them, so `DEFAULT_CLIENT_NAME='deckent-mcp-client'` / `DEFAULT_CLIENT_VERSION='1.0.0'` (`:31-32`) always win. — The override options are inert; the handshake identity (`:63`) is effectively a constant.

- [dormant|med] `registry.clear()` is a public method with no external production caller — `src/mcp-client/registry.ts:58` — `clear(server)`; the only in-`src/` invocation is `register()`'s own internal call at `:47` (`this.clear(server)`); externally it is exercised only by `tests/mcp-client/mcp-registry.test.ts:79`. — Production refresh (`registerNamespaced → register`, chat-mcp-bridge.ts:164) relies on `register()`'s built-in clear; the standalone public `clear()` is never called from production code.

- [inconsistent|med] Module/method docs describe a "caller clears then re-registers" contract that production does not follow — `src/mcp-client/registry.ts:9-11,54-57` — header: "On reconnect, the caller clears the old entries with `clear(server)` then re-registers"; `clear()` JSDoc: "Used before a reconnect to avoid stale tool entries after the server restarts." But `register()` (`:45-52`) already calls `this.clear(server)` at `:47` ("idempotent refresh"), and the sole production caller `registerNamespaced` (chat-mcp-bridge.ts:159-166) only calls `register()`, never `clear()`. — Documented external-clear workflow diverges from the actual auto-clear-inside-register behavior; the docs describe a manual step that no caller performs.

- [inconsistent|low] Stale "will produce / Task 5 will persist" future-tense type docs — `src/mcp-client/types.ts:4,9` — ":4 `McpServerDef` is the merged config record (Task 229-002 **will** produce these from `.mcp.json`)"; ":9 passed to `onCall` so Task 5 (REPL bridge) can persist it via the existing event-stream sink." — 229-002 is shipped (`config.ts loadMcpServers` produces these today), and the REPL bridge persists via its own `writeEvent` rather than the broker `onCall` (see dormant-onCall finding). Both comments describe a future/contract that no longer matches the live wiring.

- [root-cause|med] Silent-fallback: malformed MCP config JSON is swallowed to `{}` with no diagnostic — `src/mcp-client/config.ts:21-23` — `} catch { return {}; }` inside `readMcpJson`. — A JSON typo in `.mcp.json` / `.mcp.local.json` / `~/.deckent/mcp.json` produces an empty servers map with zero warning; the user sees "no MCP servers" instead of "your config is invalid". Trust-without-signal failure mode (a parse error is indistinguishable from "file absent" at `:10`).

- [root-cause|low] Trust-without-verify: parsed config cast to `McpServersMap` with no per-entry shape validation — `src/mcp-client/config.ts:16,18` — `return obj['mcpServers'] as McpServersMap;` / `return obj as McpServersMap;`. — No validation that each value is a real `McpServerDef` (no `transport`/`command`/`url` check); the non-`mcpServers` branch (`:18`) blindly casts the whole JSON object as the servers map. A malformed/foreign-shaped entry flows untyped to `createTransport` (broker.ts:163) where `def.transport` mismatch surfaces only at connect time.

- [dead-test|low] Under-asserting test: `onCall` mock created but never asserted, so the test name's audit-record clause is unverified — `tests/mcp-client/broker.test.ts:118-123` — `it('callTool on an unknown server throws a graceful error and emits an audit record for errors only when the call reaches the SDK', …)` constructs `new McpClientBroker({ onCall: vi.fn() })` (`:119`) then asserts only `rejects.toThrow(/not connected/)` (`:120-122`); the `vi.fn()` is never referenced again (no `expect(fn).not.toHaveBeenCalled()`). — The "emits an audit record for errors only when the call reaches the SDK" half of the test name is not actually checked; the mock is inert. (The other broker/registry/config tests are hermetic and real — InMemoryTransport SDK round-trip + tmpdir file I/O — not mock-only/tautological.)

## Summary

A small (≈398 LoC), cleanly-layered subsystem that is genuinely wired into the REPL MCP path (`connect`/`listTools`/`callTool`/`resolve`/`register`/`listForServer`/`loadMcpServers` all have live production callers) and ADR-008-compliant (broker/registry do not import event-stream/each-other). No fully-orphan module. The issues are surface-area and honesty drift, not broken behavior:

- **Unwired/dormant surface (7):** `disconnect`/`disconnectAll` (med — no production teardown → session-lifetime connection leak), `onCall`+`emitCall` (med — every production construction omits the hook; `createMcpAuditSink` has zero callers), `registry.clear()` public path (med), plus `broker.list()`, `registerConnection`, `registry.size`, `clientName`/`clientVersion` (low — test-only or default-always seams).
- **Inconsistent (2):** registry docs describe a manual clear-then-register reconnect contract that `register()`'s internal auto-clear and the sole caller contradict (med); `types.ts` future-tense docs for shipped 229-002 + the now-bypassed `onCall` persistence path (low).
- **Root-cause (2):** `config.ts:21-23` silent-fallback turns a malformed config into a silent empty map (med); `config.ts:16,18` casts JSON to `McpServersMap` with no per-entry validation (low).
- **Dead-test (1):** `broker.test.ts:118-123` creates an `onCall` `vi.fn()` it never asserts, leaving the test name's audit-record claim unverified (low).

Highest-value follow-ups: (1) wire `disconnectAll()` into REPL exit/cleanup; (2) surface a warning instead of silently returning `{}` on `readMcpJson` parse failure; (3) reconcile the registry reconnect docs with the auto-clear-in-`register` reality (or drop the now-redundant public `clear()`).
