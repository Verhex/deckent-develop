## Findings

### session-interface.ts
- [dormant|medium] healthCache is write-only — `src/core/session-interface.ts:37` — declared `private readonly healthCache = new Map<...>()`; written at l.47/107/139/149, but a repo-wide grep finds ZERO read sites. `getAvailableProviders()` returns from `this.providers`, not the cache. — The health cache is populated by `healthCheck()` but never consulted by any consumer; it is dead state that adds no value.
- [root-cause|high] `getAvailableProviders()` returns *registered*, not *healthy*, providers — `src/core/session-interface.ts:119-121` — `getAvailableProviders(): ProviderName[] { return Array.from(this.providers.keys()); }` while the JSDoc summary (l.114-115) states "Get list of available (registered + healthy) provider names." Caller `src/orchestra/sprint-controller.ts:1026` routes on `connector.getAvailableProviders()`. — Routing trusts a list labelled "available/healthy" that is actually "every registered provider" — unhealthy/unreachable providers are presented as routable (trust-without-verify; health never gates the result).
- [root-cause|medium] auth status asserted from env-var presence only; `expired` unreachable — `src/core/session-interface.ts:163-177` — `checkAuthStatus` returns `'ok'` whenever `process.env[envVar]` is a non-empty string and never validates the credential; it can only ever return `'ok'` or `'missing'`. — The type `authStatus: 'ok' | 'missing' | 'expired'` (l.25) advertises an `'expired'` state that is never produced, and `'ok'` is a trust-without-verify claim (env var set ≠ credential valid).
- [inconsistent|low] `cliVersion` hard-coded `null` — `src/core/session-interface.ts:103` — every `HealthCheckResult` sets `cliVersion: null` (also l.81 for the unregistered branch); the field is typed `string | null` but is never populated with a real version. — A reported metric that is structurally always null (hardcoded-null surface).

### siem-forwarder.ts
- [root-cause|medium] SIEM records dropped silently after retry exhaustion — `src/core/siem-forwarder.ts:146-152` — on exhausted retries the batch is dropped with only `console.error(...)` then `return` (no throw, no dead-letter, no drop metric). Combined with the default-off silent discard when no transport is set (l.134-137). — For an audit/SIEM forwarder this is a compliance silent-fallback: audit events can vanish with no durable signal a consumer can observe.

### siem-transport-http.ts
- _(No defect-class finding.)_ Transport is a fail-loud dumb pipe by design: URL validated eagerly (l.50-60), non-2xx throws (l.81-85), no internal retry (forwarder owns retry/drop), empty-batch short-circuit (l.75). Behaviour matches its documented contract; no unwired/dormant/inconsistent/root-cause line.

### siem-transport-syslog.ts
- [root-cause|low] UDP "success" is not delivery — `src/core/siem-transport-syslog.ts:84-98` — `sendUdp` resolves as soon as `socket.send` invokes its callback without an error, i.e. once the datagram is handed to the OS; UDP gives no delivery guarantee. The default protocol is `'udp'` (l.143). — The forwarder then records the batch as shipped though it may never reach the collector (trust-without-verify on the default path).

### signature.ts
- [unwired|high] `verifySignature` has zero production callers — `src/core/signature.ts:69` — repo grep shows callers only in tests (`tests/core/signature.test.ts:33`, `tests/cli/skill-publish.test.ts:124`). Production signs but never verifies: `src/cli/commands/skill-marketplace.ts:225` calls `signMessage`, yet no production path ever calls `verifySignature`. — The Ed25519 signing infrastructure produces signatures that are never checked anywhere in the running product (trust-without-verify — the signature provides no real integrity guarantee).
- [unwired|medium] `generateKeypair` (async) and the `hexToBytes` re-export are unused in production — `src/core/signature.ts:25` and `src/core/signature.ts:83` — production uses the sync `loadOrGenerateKeypair` (l.34) and `bytesToHex` (skill-marketplace.ts:10) only; `generateKeypair`/`hexToBytes` appear only in tests / internal `ed.etc.*` calls. — Exported API surface with no production consumer.
- [inconsistent|low] two divergent keypair-generation code paths — `src/core/signature.ts:27` (`getPublicKeyAsync`, in the unused `generateKeypair`) vs `src/core/signature.ts:48` (`getPublicKey`, sync, in the live `loadOrGenerateKeypair`) — two implementations of "derive a keypair", the async one dead. — Divergent duplicate logic; the maintained path is the sync one.

### skill-cache.ts
- [unwired|high] `SkillLoadingCache` class has zero production callers — `src/core/skill-cache.ts:25` — grep finds instantiations only in tests (`tests/core/skill-cache.test.ts:14`, `tests/core/non-null-safety.test.ts:121`); never wired into `SkillPoolManager` or any runtime path. Cross-confirms Phase-1 UNW-029 / UNW-A051. — A whole mtime/eviction cache module is orphaned while the live skill path re-reads disk (see skill-pool finding below).
- [inconsistent|low] eviction is FIFO-by-load, not LRU; staleness never auto-checked — `src/core/skill-cache.ts:177-194` — `_evictOldest` selects by `entry.loadedAt` and `getCached` (l.97-99) never refreshes `loadedAt`, so eviction is oldest-loaded (FIFO), not least-recently-used as external docs (`docs/architecture/...`) describe; `isStale()` (l.128) is never consulted inside `getCached()`. — Were the class wired, `getCached` would return content without a freshness check and evict the wrong entries relative to the "LRU" label.

### skill-pool.ts
- [root-cause|high] every accessor re-scans the whole skills dir from disk (no cache) — `src/core/skill-pool.ts:32-36` (`loadSkills` does `fs.readdirSync` + per-dir `readJsonSafe`) consumed by `getSkill` (l.68), `listSkills` (l.76), `listByCategory`/`listEnabled` (l.84/91), `enableSkill`/`disableSkill` (l.100/111 → getSkill), `updateSkillStats` (l.156 → getSkill). — Each call is a full disk scan + JSON parse of all manifests; `enableSkill` triggers a scan then a save, and a following `listSkills` scans again. The cache designed to fix this (`SkillLoadingCache`) is unwired (above). Cross-confirms Phase-1 INC-027.
- [root-cause|medium] invalid / unknown-model manifests are silently dropped with no diagnostic — `src/core/skill-pool.ts:50-56` — `loadSkills` only adds a skill when `validateSkillDefinition(raw).valid`, otherwise it is skipped with no log; `model` validation (l.218-222) rejects any id not in `ALL_MODELS` (l.18). — A manifest referencing a newer/equivalent model id silently disappears from the pool (silent-fallback: skill set shrinks with zero diagnostics).
- [inconsistent|low] dead `totalUses > 0` guards — `src/core/skill-pool.ts:169,173` — `stats.totalUses += 1` at l.161 makes `totalUses` ≥ 1 unconditionally, so the `stats.totalUses > 0 ? … : 0` ternaries at l.169 and l.173 can never take the `: 0` branch. — Unreachable defensive branch (no harm, but dead logic).

### skill-registry.ts

## Summary
This cluster shows deckent's enterprise/security-adjacent surfaces are built but only half-wired. The strongest signal is a **sign-without-verify integrity gap** (`verifySignature` has zero production callers while skills are signed) and a **trust-without-verify routing seam** (`getAvailableProviders` returns every registered provider while its doc and caller treat the list as "healthy"). Skill loading carries real architectural debt: two orphaned subsystems (`SkillLoadingCache`, `SkillRegistry`) sit unused while the live `SkillPoolManager` re-scans the whole skills directory from disk on every accessor — the dead cache was meant to fix exactly that hot-path, and a divergent JSON-vs-manifest persistence split (CORE-W3) remains. The SIEM forwarder is a sound fail-safe shell but drops audit records silently after retry exhaustion, and the default UDP syslog path reports "success" without delivery — both weaken the compliance guarantee these modules exist to provide. Findings cross-confirm Phase-1 IDs UNW-029/A051/A052 and INC-027.
