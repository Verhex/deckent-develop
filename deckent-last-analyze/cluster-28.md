# core#6 — core

Files read: 8 (cross-verify.ts, debt-store.ts, debug-log.ts, decision-config.ts, decision-types.ts, deck-file.ts, deck-interpolation.ts, directive-interrogator.ts)

## Findings

### root-cause
- [root-cause|high] `core/` → `cli/` import violates ADR-008 one-way rule, surviving on advisory-soft enforcement — `src/core/directive-interrogator.ts:18` — `import { getMessage } from '../cli/helpers/messages.js';` — A core/ module imports upward from cli/. The in-file comment (lines 15-16) self-justifies it: *"the enforced check only flags `core/ → orchestra/`"* — i.e. the architectural rule (core must not depend on upper layers) is real but the `authority-enforcer` ADR-008 check only scans `core/→orchestra/`, so `core/→cli/` slips through unblocked. This is exactly the ADR-008 amendment's tracked **CORE-W1** violation. Guarantee made soft because enforcement coverage ≠ rule scope.
- [root-cause|high] One corrupt `metadata` row silently collapses the ENTIRE debt list to empty — `src/core/debt-store.ts:29` — `const meta = JSON.parse(entry.metadata || '{}') as Record<string, unknown>;` — Unlike the reconciliation loop (lines 67-68 which guards per-entry with `try/…catch { continue }`), `debtEntryToDebtItem` parses metadata WITHOUT a guard. It runs inside `filtered.map(debtEntryToDebtItem)` (line 77) under the outer `try` whose `catch` returns `[]` (lines 78-80). So a single malformed-JSON debt entry throws → the whole `getDebtItems` returns `[]` → all tech-debt silently disappears from every consumer (status, doctor, finalizer). Silent-fallback masking data loss.
- [root-cause|medium] Missing `.deck` secret silently leaves the literal `$DECK:KEY` placeholder as the resolved config value — `src/core/deck-interpolation.ts:21` — `if (!secret) { console.warn(...); return val; }` — On a missing secret the function warns and returns the placeholder unchanged, so a token/URL field literally becomes the string `"$DECK:CLAUDE_API_KEY"` and is handed to downstream auth/HTTP as if real. Trust-without-verify: downstream gets a bogus value instead of a hard failure, surfacing later as a confusing 401/connect error. (Also bypasses both `debug-log.ts` and i18n by using raw `console.warn`.)
- [root-cause|medium] Synchronous subprocess spawn blocks the event loop, against ADR-087 async-I/O standard — `src/core/deck-file.ts:187` — `const result = execSync('git ls-files --error-unmatch .deck', { cwd: projectRoot, ... });` — `execSync` is a blocking child-process spawn (same class as the `spawnSync` the hermeticity rule forbids). Called from `doctor.ts:1183` and `doctor-checks.ts:383`. ADR-005 (sync I/O) is deprecated and ADR-087 mandates async; the rest of the module is also fully sync fs (`readFileSync`/`writeFileSync`/`appendFileSync`/`mkdirSync`) but `execSync` is the salient event-loop blocker.
- [root-cause|medium] Adversarial cross-verify is advisory-only and NEVER downgrades the evaluation — `src/core/cross-verify.ts:135` — `* Outcome of the cross-verify decision layer. Advisory metadata …` — The cross-provider "REFUTE" verification is informational by design: `CrossVerifyDecision` is explicitly advisory (lines 135-137) and the runner that consumes it states *"it is NEVER a downgrade"* / *"NEVER mutates the task's evaluation"* (`src/orchestra/cross-verify-runner.ts:7,186`). A second provider successfully refuting a high-stakes result does not block, fail, or downgrade the task — it only writes a `crossVerify` note. The "adversarial verification" guarantee is therefore soft (advisory-soft enforcement).

### unwired
- [unwired|medium] Decision/learning/collaboration config validators + default factories have zero production callers — `src/core/decision-config.ts:73` — `export function validateDecisionConfig(config: unknown): { valid: boolean; errors: string[] }` — `validateDecisionConfig`, `validateLearningConfig`, `validateCollaborationConfig`, `createDefaultDecisionConfig`, `createDefaultLearningConfig`, `createDefaultCollaborationConfig` are referenced only by `tests/core/decision-config.test.ts`; the sole non-test importer (`config-types.ts:4`) pulls only the three TYPE aliases. `config.ts` validates the `cross_verify` block inline (config.ts:850-865) but never invokes these dedicated validators — so the `decision_engine`/`collaboration`/`learning` config blocks are accepted without their own validation, and their defaults are never materialized via these factories.
- [unwired|low] `INTERROGATION_MESSAGE_KEYS` is consumed only by its test — `src/core/directive-interrogator.ts:63` — `export const INTERROGATION_MESSAGE_KEYS = [ 'interrogate.intro', 'interrogate.q_pain', … ]` — Repo-grep shows the only reader is `tests/core/directive-interrogator.test.ts`. Runtime question-building uses a SEPARATE map `CATEGORY_KEY` (line 90), so this exported list is a parallel, test-only source of truth that production never reads (see inconsistent finding below).

### dormant
- [dormant|medium] `CollaborationConfig` config block is typed into config but never read at runtime — `src/core/decision-config.ts:29` — `export interface CollaborationConfig { parallelPipelines: boolean; sharedMemoryEnabled: boolean; conflictStrategy: … }` — It is wired into `ProjectConfig.collaboration` (`config-types.ts:245`) but a repo-wide grep for `.collaboration` / `createDefaultCollaborationConfig` / `validateCollaborationConfig` finds no production consumer — the knob is defined, documented and validated-in-isolation yet has no runtime effect.

### inconsistent
- [inconsistent|medium] `getDebtItems` is a read-named accessor that mutates the DB on every call — `src/core/debt-store.ts:70` — `store.update(e.id, { status: 'resolved' }); e.status = 'resolved';` — A function documented as *"Load tech-debt items"* / *"DB-first debt accessor"* performs writes (lazy auto-resolve of stale rollback rows) inside the read path. Hidden write side-effect in a getter — every debt read can mutate persistent state.
- [inconsistent|low] In-code verifier-priority default (4 providers) diverges from the documented config default (3) — `src/core/cross-verify.ts:97` — `export const DEFAULT_VERIFIER_PRIORITY: readonly ProviderName[] = ['codex', 'gemini', 'claude', 'ollama'];` — The comment (line 92) and `config-types.ts:83` both state the config default as `['codex','gemini','claude']` (no `ollama`). So omitting `verifier_priority` falls back to a 4-entry list, but materializing the documented config default yields 3 — two "defaults" for the same setting.
- [inconsistent|low] Two parallel debug-logging facilities; the scoped one in this cluster has a single caller — `src/core/debug-log.ts:53` — `export function createDebugLog(module: string): DebugLogger` — `createDebugLog` (DECKENT_DEBUG-gated, scoped, stderr) is imported by exactly ONE production module (`src/core/memory-query.ts`), while a separate `debugLog` from `core/utils.ts` is the de-facto logger used by 20+ modules. Duplicate-divergent implementations of the same concern; the scoped variant is near-dead.
- [inconsistent|low] Overlapping learning toggles/limits split across two config interfaces — `src/core/decision-config.ts:6` — `learningEnabled: boolean;  // default true` … `learningMaxSprints: number;  // default 10` — `DecisionEngineConfig` carries `learningEnabled` + `learningMaxSprints(=10)` while `LearningConfig` (line 15) independently carries `enabled` + `maxSprintsToKeep(=10)` for the same learning concept — duplicate, separately-defaulted knobs that can drift out of sync.
- [inconsistent|low] `INTERROGATION_MESSAGE_KEYS` and `CATEGORY_KEY` are dual sources of truth that can drift — `src/core/directive-interrogator.ts:90` — `const CATEGORY_KEY: Record<InterrogationCategory, string> = { pain: 'interrogate.q_pain', … }` — Runtime resolves question keys from `CATEGORY_KEY`; the exported `INTERROGATION_MESSAGE_KEYS` (line 63) re-lists the same 5 q-keys plus `intro`/`draft_header`. Nothing keeps them in sync — a new lens added to `CATEGORY_KEY` would silently miss the exported contract list.
- [inconsistent|low] `DecisionLogEntry.step` typed as unconstrained `number` despite a documented 1-6 contract — `src/core/decision-types.ts:40` — `step: number;  // 1-6` — `createDecisionLogEntry(step, …)` (line 96) accepts and stores any number with no clamp/validation; the "1-6" invariant in the comment is unenforced by the type.

## Summary
Bu core#6 cluster'ı, deckent'in "tanımlanmış ama bağlanmamış" config/altyapı katmanlarını ve yumuşatılmış garantilerini gösteriyor: decision/learning/collaboration için ayrı validator+factory'ler ve `CollaborationConfig` knob'u tanımlı fakat hiçbir production path onları çağırmıyor (config blokları kendi validator'larından geçmeden kabul ediliyor). En kritik iki bulgu veri/mimari bütünlüğüne dokunuyor: tek bir bozuk `metadata` satırı `getDebtItems`'i sessizce boş listeye düşürüyor (tüm tech-debt kayboluyor), ve `core/→cli/` importu (directive-interrogator.ts:18) ADR-008'i ihlal ediyor ama enforcement yalnız `core/→orchestra/` taradığı için advisory-soft kalıyor — bu, deckent'in kendi mimari kurallarını advisory tuttuğunda nasıl drift ettiğinin temsilî örneği. Genel desen: zengin config yüzeyi + güvenli-degrade tercihleri, ama sessiz-fallback'ler (eksik secret → literal `$DECK:` placeholder, bozuk debt → []) gerçek hataları gizliyor ve cross-verify gibi "adversarial" özellikler bilerek bilgilendirici/non-blocking bırakılmış.
