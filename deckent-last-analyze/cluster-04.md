## Findings
- [root-cause|high] Crash-recovery defined but never wired into boot — `src/orchestra/autonomous/mission-store/sqlite-mission-store.ts:37` — `recover()` runs `UPDATE work_items SET status='pending' ... WHERE status='running'`, but the v2 boot path `runV2Engine` calls only `store.migrate()` (`src/orchestra/autonomous/mission-store/mission-engine-wire.ts:108`), never `store.recover()`; the sole caller repo-wide is `tests/orchestra/autonomous/mission-store/sqlite-mission-store-schema.test.ts:28`. — A work-item claimed by a worker that crashes mid-run stays `running` forever; `queryDue` only returns `status='pending'` (`sqlite-mission-store.ts:113`), so crash-orphaned items are never re-dispatched. The recovery method exists and is tested in isolation, yet is dead at runtime — the durability guarantee is hollow.
- [root-cause|medium] Auto-vs-park gate trusts free-text keyword matching — `src/orchestra/autonomous/policy-gate.ts:44` — `computeEntryEffectClass` decides `critical-irreversible`/`compensable` only by regex over `entry.spec.description` (`RE_IRREVERSIBLE` at `:15`); a `task`-kind entry with any `scopeDir` whose description dodges that keyword list falls through to `if (scope) return 'reversible'` (`:61`), and `reversible ∈ AUTO_SAFE` (`:11`) so `decidePolicy` returns `auto` without human approval (`:79`). — The ADR-040 default-deny / G2-G3 approval guarantee is only as strong as a hardcoded keyword list: a genuinely irreversible action phrased to avoid `publish|deploy|force-push|payment capture|send email` auto-executes. Effect classification is a heuristic on attacker/author-controlled text, not a verified property.
- [inconsistent|medium] Divergent fail-safe defaults inside the same gate — `src/orchestra/autonomous/policy-gate.ts:75` — `decidePolicy(entry, effect: EffectClass = 'reversible')` defaults `effect` to the auto-safe `reversible`, whereas the unknown/ambiguous case of `computeEntryEffectClass` defaults to `critical-irreversible` (`:64`, park). — The two halves of the policy gate point their fail-safe in opposite directions. A caller that invokes `decidePolicy(entry)` and omits `effect` on a `risk-tagged` entry auto-runs — contradicting the module's stated default-deny posture. Currently latent (both live callers pass the effect explicitly: `src/orchestra/process-controller.ts:139`, `src/orchestra/autonomous/runtime-loop.ts:450`), so it is a foot-gun, not a live bug.

## Summary
This cluster is the autonomous-v2 backbone — durable mission store, reactive ingress (nervous/repo/webhook → backlog), and the auto-vs-park policy gate — and it is mostly well-wired (`projectMission`, `SqliteMissionStore`, `makeReactiveIngester`, `makeNervousReactiveSource`, `decidePolicy`, `loadReactiveMap` all have real CLI/API/runtime callers). The two material weaknesses are guarantee-softening: crash recovery is implemented and unit-tested but the boot path never calls `recover()`, so worker crashes silently strand `running` items; and the approval gate's safety rests on a hardcoded keyword regex over free-text descriptions, with the gate's own two halves defaulting their fail-safe in opposite directions. The reactive layer carries two pieces of dead payload (`dedupKey`, `ReactiveEvent.metadata`) that are declared/populated but never read, so a configured dedup override or event metadata is silently dropped. No test file is in this cluster's read-scope, so the dead-test category is legitimately empty (the `dedupKey` fixture concern is folded into the dormant finding above).
