### base-connector.ts
- [unwired|low] `isStarted` getter has zero production callers — `src/connectors/base-connector.ts:86` — `get isStarted(): boolean { return this.started; }`. Repo-grep `\.isStarted` returns only this definition + `tests/connectors/base-connector.test.ts` (:77,:81,:85,:93,:116,:124); the other hits (`src/nervous/observer.ts:164`) are an unrelated class. No production code reads `BaseConnector.isStarted` — test-only public surface.
- [root-cause|medium] `emitMessage` swallows EVERY handler error silently (no log / counter / emit) — `src/connectors/base-connector.ts:77-82` — `try { handler(msg); } catch { /* Handler errors should not crash the connector */ }`. Isolation is intentional (asserted by `base-connector.test.ts:127`), but the empty catch discards the error with zero observability: a handler that always throws (e.g. a broken command router) fails invisibly forever — there is no signal upstream that inbound messages are being dropped.
- [dormant|low] `startOutbound` default is a no-op distinction for every non-Telegram connector — `src/connectors/base-connector.ts:45-47` — `async startOutbound(config) { await this.start(config); }`. Only `src/connectors/telegram.ts:140` overrides it; Discord (and any other) inherit the delegate, so `startOutbound === start` there. The outbound/inbound split that `connector-bootstrap.ts:90` relies on (`connector.startOutbound?.bind(...) ?? connector.start.bind(...)`) only actually differs for Telegram.

### bot-completion.ts

### bot-daemon.ts
- [root-cause|low] `stopBot` SIGTERMs but never clears the pidfile itself — `src/connectors/bot-daemon.ts:60-65` — `process.kill(pid, 'SIGTERM')` then returns; cleanup relies on the listener's own `clearBotPid` on graceful exit (`:48-55`). ### bot-humanizer.ts
- [root-cause|medium] Correctness gate verifies ONLY approve/reject/accept ids — numbers & paths are prompt-enforced only (trust-without-verify) — `src/connectors/bot-humanizer.ts:120-121` — `const must = criticalTokens(text); if (must.some((tok) => !trimmed.includes(tok))) return chunkMessage(text, maxChars);`. `criticalTokens` (`:76-85`) matches ONLY `/\b(?:approve|reject|accept)\s+(\S+)/`. But the module's stated invariant (`:9-11` "NEVER drop actionable items — ids ... numbers, paths survive verbatim") and the prompt (`:60-61` "Preserve EVERY id, command, number, and file path EXACTLY") promise more. A weak model that drops/alters a number or file path passes the gate undetected — only the id class is actually post-verified; numbers/paths are trusted to the LLM.

## Summary
This connectors#1 cluster (the Telegram/Discord bot core) is functionally live and unusually safety-conscious — the gated dispatcher (`bot-agentic.ts`), durable park store (`bot-action-store.ts`), execute-time TTL+sprint re-verify (`connector-bootstrap.ts:185`) and humanizer raw-fallback (`bot-humanizer.ts`) all work. The debt is two-shaped. (1) **Unwired/dead surface left behind by refactors**: `approvalCallbackData` (the button-BUILD half whose docstring still claims a "lockstep" guarantee that nothing enforces), the `chat-bridge.ts:210` `chunkMessage` backward-compat re-export (every consumer already imports from `message-format.js`), `BaseConnector.isStarted` (test-only), and the `makeGatedDispatcher` no-probe legacy branch that its sole caller never triggers. (2) **Trust-without-verify / silent-degrade root causes**: the humanizer's correctness gate verifies only approve/reject ids while the prompt+header promise numbers and paths too; `emitMessage` swallows handler errors with zero observability; `resolveBotProviders` and the bootstrap loops silently drop misconfigured providers/connectors down to passthrough/`null` with only stderr; and `defaultSubscriptionProvider` hardcodes `stopReason: 'end_turn'`. Plus a structural smell — the outbound (`buildConnectorTargets`) and inbound (`bootstrapConnectorCommands`) bringup loops are duplicated divergent code, and `summarizeArgs`/`summarize` are the same helper with 120- vs 60-char caps. Highest-value fixes: (a) verify numbers/paths (or narrow the documented invariant) in the humanizer gate, and (b) either wire or delete `approvalCallbackData` so the live button path can't silently drift from the parser.
