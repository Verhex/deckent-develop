### root-cause
- [root-cause|high] Plugin code is `import()`-executed with trust-without-verify by default — `src/core/plugin-hooks.ts:142` — `loadHookModule` does `await import(fileUrl)` to run arbitrary plugin code. Because the security gate is opt-in (`:174` `if (securityConfig)`) and the only live caller passes no options (`sprint-controller.ts:876`), hook modules execute with NO sandbox scan and NO signature check. Even when wired, `plugin_require_signature` defaults `false` (`plugin-hooks.ts:226`, `plugin-loader.ts:62`), so unsigned plugins are only warned (`plugin-loader.ts:138`), not blocked. The defense-in-depth promised in `plugin-loader.ts:1-6` is unenforced in production. (Root cause of the dormant-security finding.)
- [root-cause|medium] pid-reuse "zero-tolerance" guard degrades to a no-op off Linux — `src/core/pid-ownership.ts:22` — `if (process.platform !== 'linux') return null;` makes `processStartToken` always null on macOS/Windows → `verifyPidOwnership` returns `'unknown'` (`:68-71`) → callers fall back to liveness-only (`src/orchestra/sprint-pid-manager.ts:128`). macOS is a documented supported platform (IDENTITY.md: "Platform: macOS, Linux, WSL2"). The catastrophe the module exists to prevent — SIGKILL of a foreign process holding a recycled pid (`pid-ownership.ts:3-8`) — remains possible on macOS; the guarantee silently softens to best-effort.
- [root-cause|medium] CI coverage metric is hardcoded 0 — `src/core/plugin-hooks.ts:675` — `runPreSprintValidation` always writes `coverage: 0` (baseline `:675`; all returns `:619/:638/:660/:708`), and `runAfterSprintCiReport` propagates `coverage: baselineCoverage` (`:813`, itself 0) with `coverageDelta: 0` (`:818`). Coverage is never measured despite `track_coverage` defaulting `true`, so every CI baseline/report emits a constant-0 coverage that downstream consumers (ci-learning / doctor trend) read as real signal.
- [root-cause|low] pre-sprint CI gate is soft-by-default on test failure — `src/core/plugin-hooks.ts:284` — `DEFAULT_CI_GUARDIAN_CONFIG.block_on_test_fail: false`, so `runPreSprintValidation` (`:653`) does NOT block a sprint when the full suite fails (only `block_on_tsc_fail`, default true, blocks). A red test suite passes the pre-sprint gate unless the user flips the flag; the failure is downgraded to a stderr warning (`:690-693`) and the sprint proceeds.

## Summary
This cluster is deckent's plugin/CI-guardian/process-liveness plumbing, and the audit shows a recurring pattern: **safety machinery exists but is wired loosely or not at all.** The plugin security layer (sandbox AST + SHA-256 signature) is fully implemented in `plugin-loader.ts` yet completely bypassed because the only live `loadPluginHooks` call omits the options that would enable it — so plugins are `import()`-executed unscanned and unsigned (root-cause high). The CI-guardian module carries a dead afterSprint report generator (`runAfterSprintCiReport`) that duplicates the live `ci-reporter.ts` writer, a `track_coverage` knob that gates nothing, a hardcoded-0 coverage metric, and a test-failure gate that is soft by default. Two concrete correctness bugs stand out beyond "soft enforcement": `validateManifest` strips `beforeTask`/`afterTask` hooks the type and loader both expect (so half the documented hook surface can never fire), and the pid-reuse "zero-tolerance" guard is a no-op on macOS — a supported platform. Net: deckent's enterprise-grade guarantees here (plugin trust, CI regression gating, pid-reuse safety) are advisory in the live path rather than enforced, matching the broader advisory-soft pattern flagged elsewhere in the codebase.
