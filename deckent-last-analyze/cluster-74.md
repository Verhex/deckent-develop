### connector-notify-adapter.ts
- [root-cause|low] `withTimeout` leaks the in-flight send when a connector hangs — `src/connectors/connector-notify-adapter.ts:90-98` + `:124-147` — `Promise.race([p, new Promise<undefined>((resolve) => { const timer = setTimeout(() => resolve(undefined), ms); … })])`. On timeout the race resolves `undefined` but the underlying send IIFE (`humanizer.toParts` + the `sendMessage` loop) keeps running detached; a truly hanging connector (`sendMessage` that never resolves) leaves a permanently-pending promise per notification. Accepted fail-safe trade-off (timer is `unref`'d, per-target `.catch`), but a latent resource accumulation under a sustained-hang platform — flagged as advisory-soft (no cancellation of the orphaned send).
- [inconsistent|low] Per-platform branding divergence: non-Telegram gets a `[deckent]` tag, Telegram does not — `src/connectors/connector-notify-adapter.ts:43` (`const head = \`${emoji} [deckent] ${n.title}: ${n.summary}\`;`) vs `:67` (`const head = \`${emoji} <b>${htmlEscape(n.title)}</b>\n${htmlEscape(n.summary)}\`;`). The plain formatter prefixes `[deckent]`; the Telegram HTML formatter drops it. Same notification renders with divergent identity across platforms (locked-in by tests `connector-notify-adapter.test.ts:124` vs `:132`). Intentional but undocumented divergence.

### discord.ts

## Summary
connectors#2 splits into a healthy inbound-command core and a sizeable layer of unwired/dead dispatch + inbound-routing scaffolding. **Functionally live & sound**: `incoming-command-resolver.ts` (durable autonomous-vs-nervous gate routing, idempotent, short-code support — disk-backed real tests), `incoming-command-router.ts` (single auth chokepoint default-deny + backlog-replay guard), `connector-notify-adapter.ts` (per-platform render, timeout + per-target isolation, lossless split), the Telegram/Discord connectors, and `message-format.chunkMessage`. **The debt is two-shaped.** (1) **Unwired / dormant surface** — the entire `ConnectorPool` class is never imported in production (the notify path deliberately bypasses it) yet carries a full 9-spec mock-only test; `WhatsAppConnector` is a guaranteed-throw scaffold never instantiated; `ConnectorId` ships phantom `'slack'`/`'email'` ids that pass webhook validation but have no connector; and most consequential — **`IncomingMessageRouter` publishes `INCOMING_MESSAGE` to an event bus with ZERO subscribers**, so the live `/api/webhooks/:connector/:key` endpoint validates+parses+routes inbound messages into a void (the docstring's promised nervous detectors do not exist). (2) **Trust-without-verify / silent-degrade root causes** — Discord `sendMessage` silently drops messages for unfetchable channels while broadcast reports success; `validateWebhookKey`'s length-mismatch decoy times `expected` not `provided`; `withTimeout` orphans hung sends; both `isHealthy` impls assert health from object-existence not a live connection; and the inbound event is mislabeled (`source:'deckent'` on the outbound `DECKENT→USER:NOTIFY` channel, contradicting its own doc). Highest-value fixes: (a) wire a real `INCOMING_MESSAGE` consumer or delete the inbound webhook→router path so it can't read as a working feature; (b) either wire or delete `ConnectorPool` + its test; (c) make Discord `sendMessage` surface the unfetchable-channel drop instead of swallowing it.
