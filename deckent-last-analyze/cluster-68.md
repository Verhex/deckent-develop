# mcp#3 — mcp code-audit (directives, docs, doctor, explain, feature-query, help, history, index, init, job-runner)

> Read-only structural audit. 10 files read in full. Every finding carries `file:line` + proving snippet.
> Zero-caller/dormant claims grep-verified across `src/` (def + test excluded).
> Categories: unwired | dormant | inconsistent | dead-test | root-cause.
> Scope note: this cluster is the **MCP tool-registration layer** (`src/mcp/tools/`) — thin handlers that wrap `cli/` + `orchestra/` + `core/` logic and serialize JSON responses for the MCP stdio transport.

## Findings

### unwired (zero production callers — grep-verified)

- [unwired|low] `readJobState` is exported but has no external production caller — `src/mcp/tools/job-runner.ts:46` — `export function readJobState(projectRoot: string, jobId: string): JobState | null {`. Grep over `src/` (def+test excluded) finds the symbol only at its definition (`:46`) and its own internal self-call inside `readLatestJobState` (`:95` `return readJobState(projectRoot, jobId);`). No consumer outside the module imports it (`start.ts`/`run.ts`/`sprint-runner-entry.ts` import `writeJobState`/`buildTaskSummaries`; `status.ts` imports `readLatestJobState`). The remaining references are tests (`tests/mcp/job-runner.test.ts`, plus `vi.fn()` mocks) and docs. Not dead (the internal self-call exercises it), but the `export` keyword serves no caller — it could be module-private.

### dormant (defined-but-unread / no-op gate in production)

- [dormant|medium] The `auto` input of `deckent_init` is declared, documented, then explicitly discarded — `src/mcp/tools/init.ts:80` — `// auto: hint that project stack should be auto-detected (already default behavior in MCP)` / `void auto;`. The schema advertises it as a real mode (`:73` `auto: z.boolean()...describe('Auto-detection mode: skip interactive wizard, detect project stack automatically and apply defaults.')`), but no code path reads it; it is only echoed back inside the response payload (`:263` `enrichResponse('init', { ...auto, ... })`). A caller passing `auto:true` expecting stack auto-detection gets a no-op gate that silently changes nothing.

### inconsistent (duplicate / divergent / conflicting definitions)

- [inconsistent|high] Three divergent sources of truth for the MCP tool catalog, all hand-maintained and drifted — the live registry registers **35** tools (`src/mcp/tools/index.ts:34-66` `registerTools()`; `grep -c server.registerTool src/mcp/tools/**` = 35), but the `deckent_help` static catalog lists only **23** — `src/mcp/tools/help.ts:48` `const TOOLS: HelpToolInfo[] = [` … `:72` (23 entries, last is `deckent_models`). Missing from the help catalog: `deckent_watch`, `deckent_usage`, `deckent_process`, `deckent_autonomous`, `deckent_audit`, `deckent_recover`, `deckent_feature_query`, and all five `deckent_nervous_*` (`nervous.ts:202,247,315,347,401`) = 12 registered tools the help tool will never surface. A third source (`src/mcp/server.ts:27` `## Tools (35)`) headers 35 but its own test enumerates only 32 (see dead-test). No code derives any of these from `registerTools`, so every new tool requires three manual edits or the catalog silently rots.

- [inconsistent|medium] `deckent_set_directives` counts tasks with two divergent regexes that can disagree — `src/mcp/tools/directives.ts:10` `const headers = content.match(/^##\s+(Görev|Task)\s+\d+[:\s].*/gm) ?? [];` (drives `breakdown`) vs `:66` `const taskCount = (content.match(/^##\s+(Görev|Task)\s+\d+/gm) ?? []).length;`. The breakdown regex requires a `[:\s]` delimiter after the task number; the count regex does not. The response returns BOTH (`:70` `{ ..., taskCount, breakdown, estimatedModels }`), so a header the count matches but the breakdown rejects (e.g. `## Task 5X`) makes `breakdown.code+docs+test+analysis !== taskCount` — two answers to "how many tasks" in one payload.

- [inconsistent|low] `estimatedModels` advertises an opus/sonnet/haiku split that has no relationship to the actual router — `src/mcp/tools/directives.ts:21-28` `computeEstimatedModels` uses fixed ratios (`opus: Math.ceil(complex * 0.4)`, `sonnet: Math.ceil(complex * 0.6) + …`) and is surfaced to the caller (`:70`). Real per-task model assignment runs through `routeTaskV2` / `model-registry` / `mode-presets` at plan time; this heuristic is computed independently from header keyword-matching and will diverge from what `deckent_plan` actually assigns — a confident-looking estimate that is decorrelated from reality.

- [inconsistent|low] `feature-query.ts` imports the legacy `zod` entrypoint while 24 of 26 sibling tool files use `zod/v4` — `src/mcp/tools/feature-query.ts:7` `import { z } from 'zod';` vs the cluster norm `import { z } from 'zod/v4'` (`directives.ts:3`, `docs.ts:6`, `doctor.ts:1`, `explain.ts:3`, `history.ts:3`, `init.ts:3`, …). The only other `'zod'` importer in `src/mcp/tools/` is `models.ts:5`. Two schema-builder entrypoints coexist in the same registration layer — a validation-semantics drift hazard.

- [inconsistent|low] `deckent_help` emits hardcoded Turkish next-action strings inside an otherwise all-English structured response — `src/mcp/tools/help.ts:181` `return 'deckent_init ile projeyi baslatin';` / `:184` `'deckent_set_directives ile sprint hedeflerini yazin'` / `:187` / `:190` / `:192`. The surrounding `TOOLS`/`RESOURCES`/`workflows` payload is English; `nextAction` is TR with no `getMessage()`/lang plumbing — a mixed-language response and a CLAUDE.md "i18n-FIRST, never hardcode user-facing strings" violation in the same handler.

- [inconsistent|low] `deckent_init` `created[]` over-reports — it pushes filenames unconditionally regardless of whether anything was written — `src/mcp/tools/init.ts:101` `created.push(dir.replace(root + '/', '') + '/');` (inside the `ensureDir` loop), `:156` `created.push(DECKENT_FILE);` (after a `writeFile` that no-ops when the file exists and `force` is false), `:162` `created.push(AGENTS_FILE, CLAUDE_FILE);` (after `writeIfNotExists`), `:168` `created.push('.claude/rules/', …)`. Because `init` is idempotent/safe-to-rerun, a re-run on a fully-initialized project still reports every path as `created` — the field name claims creation the code never verified.

- [inconsistent|low] `deckent_docs` update is asymmetric — protected sections can be added but never removed — `src/mcp/tools/docs.ts:101` handles `addProtectedSections` (`entry.protectedSections = [...new Set([...(entry.protectedSections ?? []), ...addProtectedSections])]`) but there is no `removeProtectedSections` branch, and the schema (`:25-27`) declares `addAutoSections`/`removeAutoSections`/`addProtectedSections` with no `removeProtectedSections`. Auto sections are add+remove symmetric; protected sections are add-only, so a section protected by mistake cannot be un-protected through `action=update`.

### dead-test (mock-only / stale / tautological / tests over weak assertions)

- [dead-test|medium] The only assertion on the `deckent_help` tool-catalog size is a lower bound so loose it can never catch the 23-vs-35 drift — `tests/mcp/tools/help.test.ts:316` `expect(data.tools.length).toBeGreaterThanOrEqual(16);`. The static catalog has 23 entries and the registry has 35; `>= 16` would still pass if the catalog were cut nearly in half. No test anywhere asserts `help.ts` `TOOLS` completeness against `registerTools()` (grep for `registerTools` in `tests/mcp/` returns nothing), so the divergence reported above is entirely unguarded.

- [dead-test|low] The MCP-instructions catalog test is internally contradictory yet green — `tests/mcp/help.test.ts:11-13` asserts `DECKENT_MCP_INSTRUCTIONS` contains `'## Tools (35)'`, while `:30-69` enumerates a 32-name list and asserts `expect(expectedTools).toHaveLength(32)`. 35 ≠ 32: the three registered tools `deckent_autonomous`/`deckent_process`/`deckent_usage` are never checked for presence in the instructions, so the test affirms the "35" header without verifying 35 tools are actually listed. (SUT is `src/mcp/server.ts`, adjacent to this cluster; cited because it codifies the same catalog-SSOT rot as `help.ts`.)

### root-cause (advisory-soft / trust-without-verify / silent-fallback / hardcoded-0-metric)

- [root-cause|medium] A missing result file is silently reported as a passing `DONE` task — `src/mcp/tools/job-runner.ts:65` `let evaluation = 'DONE';` then `:67` `if (existsSync(resultPath)) { … if (result.selfAssessment) evaluation = result.selfAssessment; … }`. When `task-<id>.result` is absent (worker died before writing, or post-cleanup), `evaluation` stays the optimistic `'DONE'` default. `buildTaskSummaries` feeds the persisted job state (`src/orchestra/sprint-runner-entry.ts:252` `const tasks = buildTaskSummaries(projectRoot, sprint.tasks)`), so a task that produced no result surfaces in `deckent_status`/job history as completed — a trust-without-verify default that masks worker failure as success.

- [root-cause|medium] `deckent_explain <sprintId>` silently substitutes a different sprint's learnings when the requested retro is missing — `src/mcp/tools/explain.ts:35-37` `const retros = store.getByType('retro').sort((a,b) => (b.sprint_num ?? 0) - (a.sprint_num ?? 0)); return retros[0]?.content ?? null;`. The preceding `getById(\`retro-sprint-${sprintNumber}\`)` (`:33`) is tried first, but on miss the function returns the **most recent** retro's content with no flag. The sprint header/metrics come from the requested sprint's log (`:91-98`) while `learnings` (`:115-118`) can come from an entirely different sprint — `deckent_explain sprintId=42` can render sprint-300's learnings under a "Sprint 42" heading. The fallback is even documented as intended (`:23` JSDoc), which makes the silent sprint-mismatch a designed behavior, not an oversight.

- [root-cause|low] `deckent_doctor` reports `healthScore: 0` (total failure) when zero checks ran — `src/mcp/tools/doctor.ts:66` `const healthScore = totalChecks > 0 ? Math.round((passedChecks / totalChecks) * 100) : 0;`. If `response.checks` is empty/absent (`:63-64` `checks?.length ?? 0`), the score collapses to a hardcoded `0`, indistinguishable from "all checks failed." Low severity because `runDoctorChecks` normally returns a populated `checks` array, but the empty/error path conflates "no data" with "catastrophic health."

## Summary

10 MCP-tool files audited (all read in full); zero source changes. `tsc --noEmit` is unaffected (no source touched); the dedicated test files for this cluster pass. **12 findings**:

- **unwired (1):** `job-runner.ts:46` `readJobState` exported but only self-referenced (`:95`) + tests — over-export, not dead.
- **dormant (1):** `init.ts:80` `void auto;` — the `auto` input is declared + documented but discarded (no-op gate, only echoed back).
- **inconsistent (7):** the headline is the **3-way tool-catalog drift** — registry 35 (`index.ts`) vs help static 23 (`help.ts:48-72`) vs instructions "35"/enumerated-32 (`server.ts` + test) with 12 tools absent from the help catalog; plus directives' two divergent task-count regexes (`:10` vs `:66`), the `estimatedModels` heuristic decorrelated from `routeTaskV2`, `feature-query.ts:7` `'zod'` vs the cluster's `'zod/v4'`, hardcoded-TR `nextAction` strings (`help.ts:181-192`), `init` `created[]` over-reporting on idempotent re-run, and `docs` update's add-only protected sections.
- **dead-test (2):** `tools/help.test.ts:316` `>= 16` lower-bound can never catch the 23-vs-35 catalog drift; `help.test.ts` asserts both "Tools (35)" and a 32-item list (35≠32, three tools unverified).
- **root-cause (3):** `job-runner.ts:65` missing result ⇒ `'DONE'` (failure masked as success — highest-leverage); `explain.ts:35-37` missing retro ⇒ most-recent retro's learnings under the wrong sprint header (silent sprint-mismatch); `doctor.ts:66` zero checks ⇒ hardcoded `healthScore 0`.

Highest-leverage: the **`evaluation = 'DONE'` default** at `job-runner.ts:65` — it converts an absent/lost worker result into a reported success in job state and `deckent_status`, the one finding with real correctness impact on Brain's view of a sprint. The **3-way catalog SSOT drift** is the broadest maintainability defect (every new tool needs three manual edits and the only guarding test is a `>= 16` no-op). The **explain retro-fallback** (`:35-37`) silently misattributes learnings across sprints. Note: `addDoc` (`docs-config.ts:127-145`) was checked — `add` dedupes by id/path and updates in place, so `docs.ts` `idempotentHint: true` is correct (no finding); all 10 `register*Tool` exports are wired through `index.ts` → `server.ts:140` (clean).
