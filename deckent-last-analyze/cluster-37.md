Central fact for this cluster: there are **two parallel notification subsystems**. The OLD one (`notifications.ts` → `NotificationDispatcher` + `slack.ts`/`webhook.ts`/`discord.ts` providers) is **never instantiated in production** (only tests). The NEW one (`notification-dispatcher.ts` → `NotifyDispatcher` + `notify-adapters/*` + `notify-bootstrap.ts` + `notify-registry.ts`) is **live** (wired from `start.ts`, `autonomous.ts`, `mcp/server.ts`, `sprint-runner-entry.ts`).

## Summary
This cluster is dominated by a clean split between a **dead old notification subsystem** and a **live new one**: `notifications.ts` (`NotificationDispatcher`) plus the `slack.ts`/`webhook.ts` providers are never instantiated outside tests, and their entire `config.notifications` surface (`config-types.ts:247`) is typed but read by nothing — a user-facing config knob that silently does nothing (confirms Phase-1 UNW-A046). The live path (`NotifyDispatcher` + `notify-adapters/*` + `notify-bootstrap.ts` + `notify-registry.ts`) works but carries real soft-guarantee gaps: the CLI parent-TTY adapter is silently dormant on macOS because bootstrap force-sets `DECKENT_PARENT_PID` and the Linux `/proc` probe defeats the stderr fallback; the file adapter asserts availability without verifying writability and then swallows write failures; and the three live adapters disagree on whether `send()` is internally fail-safe. The persistent deckent-wide signature here is **advisory/silent-success** — both dead providers (slack/webhook) treat any resolved HTTP POST as delivered without checking status, and every adapter degrades to a swallowed debugLog rather than a surfaced error.
