- [dormant|medium] `DocUpdater.tier` is required but never read at runtime — `src/orchestra/doc-updaters/types.ts:29` — `tier: 1 | 2 | 3;` is set on every updater (changelog.ts:63 `tier:1`, health-check.ts:9 `tier:2`, etc.). `runAllUpdaters` (registry.ts:17-27) never inspects `u.tier`, and each `shouldRun` gates on the **string keys** `ctx.config.auto_docs?.tier1`/`tier2` (changelog.ts:68, health-check.ts:14, readme-metrics.ts:12) — not on the numeric `tier` field. Repo-grep over `src/**` shows no `u.tier`/`updater.tier` read. The field is decorative metadata only.

- [dormant|medium] `DocUpdater.internal` is required but never read at runtime — `src/orchestra/doc-updaters/types.ts:30` — `internal: boolean;` (health-check.ts:10 `internal:true`, others `false`). Internal-only gating is actually done via `ctx.isInternalProject` (health-check.ts:15 `if (!ctx.isInternalProject) return false;`), set from `existsSync('DECKENT-MASTER-BLUEPRINT.md')` (sprint-docs-updater.ts:72). `runAllUpdaters` never reads `u.internal`; repo-grep over `src/**` finds no consumer of the field. Two parallel "is-this-internal" mechanisms exist; only `isInternalProject` is live.

- [dormant|low] `DocUpdateContext.store` declared for updaters but never populated on the registry path nor read by any of the 7 updaters — `src/orchestra/doc-updaters/types.ts:12` — `store?: MemoryStore;`. The ctx built for `runAllUpdaters` omits it: `sprint-docs-updater.ts:114` → `const ctx = { projectRoot, sprintResult, config, isInternalProject, results };` (no `store`). None of changelog/health-check/metrics/readme/sprint-log reads `ctx.store`. The field is consumed only by the separate managed-docs runner, so for this cluster it is permanently `undefined`.

- [dormant|low] `usageData` branch is unreachable in production (and inside the unwired updater) — `src/orchestra/doc-updaters/metrics-updater.ts:70-73` — `const usageData = (sprintResult as unknown as Record<string, unknown>).usageData as ...; if (usageData && usageData.totalCalls > 0) {`. `usageData` is not a field of `SprintResult` (accessed via an `as unknown as` cast that bypasses the type). Repo-grep shows the only writer is the test (`metrics-updater.test.ts:175`); nothing in `src/**` ever attaches `.usageData` to a sprint result, so `usageData` is always `undefined` and the branch never runs — double-dead since the host updater is itself unregistered.

- [root-cause|high] `runAllUpdaters` swallows every updater exception silently with an empty catch — `src/orchestra/doc-updaters/registry.ts:22-26` — `try { return u.run(ctx); } catch { return { file: u.targetFile, updated: false, reason: 'error' }; }`. The error object is not bound, not logged, not re-thrown. Any updater failure (fs permission, bad regex, malformed sprint data) is invisibly reduced to `reason:'error'` and the sprint proceeds as if docs were handled. This makes the "docs auto-update after every sprint" guarantee soft — there is no observable signal that a doc write actually failed.

- [root-cause|high] Fabricated README "tests" count — coverage% × 10 written as a test total to a user-facing doc — `src/orchestra/doc-updaters/readme-metrics.ts:35-39` — `if (metrics.coveragePercent > 0) { content = content.replace(/\d+\+?\s+tests?/g, \`${Math.round(metrics.coveragePercent * 10)}+ tests\`); }`. Test count is invented from coverage percentage (e.g. 88.6% coverage → "886+ tests"), which has no relationship to the real test total. The replacement is unverified and writes a fictional metric into the public README. (The unwired sibling at metrics-updater.ts:48-51 fabricates differently — `totalTasks * 10` — see inconsistent finding below.)

- [root-cause|medium] Changelog sections silently truncated to 10 entries with no overflow marker — `src/orchestra/doc-updaters/changelog.ts:140,143,146` — `sections.push('### Added\n', ...dedupedAdded.slice(0, 10));` (and the same `.slice(0, 10)` for Changed/Fixed). A sprint with more than 10 added/changed/fixed items silently drops the overflow from the changelog — no "+N more" line, no log. The Keep-a-Changelog output understates what shipped, and the loss is invisible.

- [inconsistent|medium] Duplicate-divergent README updaters — same target, same sprint-count regex, divergent test-count formula — `src/orchestra/doc-updaters/metrics-updater.ts:48-51` vs `src/orchestra/doc-updaters/readme-metrics.ts:35-39` — both declare `targetFile: 'README.md'` and both replace `/\d+\s+sprints?\s+completed/g` identically, but the test-count value diverges: metrics-updater uses `${metrics.totalTasks * 10}+ tests` while readme-metrics uses `${Math.round(metrics.coveragePercent * 10)}+ tests`. They are near-copies (the design notes call metrics-updater "readme-metrics.ts kopyası"). Only readme-metrics is registered, so the divergence is latent — but if metrics-updater were ever wired, two updaters would fight over the same README region with conflicting numbers.

- [inconsistent|medium] Health-check "Tests" row is populated from `totalTasks`, not a test count — `src/orchestra/doc-updaters/health-check.ts:37,49-52` — initial table writes `\`| Tests | ${metrics.totalTasks} |\`` and the update path replaces `/\| Tests \| \d+ \|/g` with the same `metrics.totalTasks`. The row is labelled "Tests" but the value is the sprint's task count (e.g. 10), not the test-suite size. The metric label and its source diverge, producing a misleading health-check table.

- [dead-test|high] `metrics-updater.test.ts` is a 16-case, mock-only suite for the unwired `sprintMetricsUpdater` — `tests/orchestra/doc-updaters/metrics-updater.test.ts:7` — `vi.mock('node:fs', () => ({ existsSync: vi.fn(), readFileSync: vi.fn(), writeFileSync: vi.fn() }));`. The suite is fully mocked (no real fs), so it proves only that dead code behaves as written — green coverage on a code path the orchestrator can never reach. Includes `:170-183` testing the never-populated `usageData` branch via an injected cast.

- [dead-test|low] Misleading-invariant assertion — "result.updated is always true" only holds for the fresh-mock path — `tests/orchestra/doc-updaters/doc-updater-consistency.test.ts:129-132` — `it('changelogUpdater result.updated is always true', () => { const result = changelogUpdater.run(makeCtx()); expect(result.updated).toBe(true); });`. The title claims an invariant, but `changelogUpdater.run` returns `updated:false` on the idempotency path (changelog.ts:88-94, `duplicate_sprint_entry`). The test passes only because `makeCtx` mocks an empty/fresh changelog; it does not assert the "always" it names, so it gives false confidence about the duplicate-entry behavior.

## Summary
The doc-updaters registry is live (wired at `sprint-docs-updater.ts:115`), but it ships one fully-dead updater: `sprintMetricsUpdater` (92 LoC) is exported, tested, and never registered — a confirmed long-standing dead path. The `DocUpdater` interface carries two required-but-never-read fields (`tier`, `internal`) plus an unpopulated `store`/`usageData` pair, showing metadata that drifted away from runtime use. The most consequential issues are honesty-of-output ones: README "tests" counts are fabricated from coverage% (and, in the dead sibling, from task count); the changelog silently truncates to 10 entries; and `runAllUpdaters` swallows every updater error in an empty `catch`, so doc-write failures are invisible — turning the "docs auto-update each sprint" promise into a best-effort with no signal. Test debt mirrors the code debt: a full mock-only suite validates the unwired updater, and a "always true" consistency test asserts an invariant the code does not actually hold.
