### root-cause
- [root-cause|medium] Silent-fallback on destructive controls — `src/dashboard/src/components/SprintControlPanel.tsx:50-52` (kill-all), `:62-64` (single-kill), `:73-75` (cleanup) — each handler's `catch { /* silent */ }` swallows the failure with no toast/inline error; a failed "Kill All" or "Cleanup" looks identical to success (button just re-enables via `finally`). For worker-destroying actions this is trust-without-verify — the user believes workers were killed when the POST may have 500'd. (The live `DashboardPage.tsx:221-321` copy should be audited for the same pattern.)
- [root-cause|low] Directives load-failure hidden — `src/dashboard/src/components/DirectivesEditor.tsx:24-26` — `.catch(() => { /* start with empty editor on fetch failure */ })` — a failed `GET /api/directives` silently yields an empty editor indistinguishable from "no directives yet"; no error state is surfaced (unlike the save path, which sets `error` :43). The empty-overwrite risk is bounded by the `if (!content.trim()) return` save guard (:35), but the load error itself is invisible.

## Summary
This cluster is dominated by **build-but-don't-wire duplication**: three substantial components — `SprintControlPanel` (+ its 307-line test), `RefreshButton`, and the `Onboarding` wizard — are fully implemented yet have zero production callers, and `Sidebar.tsx`'s `SidebarNavLinks` is dead alongside the also-dead `AppShell` it feeds. The live dashboard re-solves the same problems inline (`DashboardPage` reimplements kill-all/cleanup; `Layout.NavLinks` reimplements the nav), so the divergence is not benign: the shipped copies are the feature-poorer ones — most visibly the **nervous pending-count badge**, which exists only in the unwired `SidebarNavLinks` and therefore never appears in the running sidebar. A second strong axis is **i18n-FIRST drift**: `Onboarding`, `SprintControlPanel`, `RefreshButton`, and `DirectivesEditor` hardcode user-facing EN while `NewSprintModal`/`SprintChart`/`Layout` correctly route through `t()`, and `ManualTokenInput`/`MemoryExplorer`/`RoutingDistribution` split the two policies inside a single file; a parallel "i18n-clean" `DirectivesPage` was added without retiring the hardcoded `DirectivesEditor`. Tests reinforce rather than catch these: 18 green tests cover the unwired `SprintControlPanel`, and one of them (`:255-273`) explicitly enshrines the silent-swallow of failed destructive POSTs as correct — the one genuine runtime risk here (kill/cleanup failures surfaced as silent no-ops). Clean counter-examples: `NewSprintModal`, `SimpleMarkdown`, `Skeleton`, `EmptyState`, `SprintChart`, and `DockPanel`'s bootstrap-token gate are correctly wired and (where user-facing) i18n-clean.
