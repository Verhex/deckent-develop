### root-cause
- [root-cause|high] Cross-verify learning guarantee is soft — no live signal source — `src/orchestra/outcome-tracker.ts:252` (`if (verdict === 'unclear') return;` followed by advisory perf/synergy updates) — the method is fully implemented and ADR-070-documented as the ROUTE-1 advisory signal ("REFUTED → negative signal … CONFIRMED → positive signal"), yet zero production code invokes it (proof: unwired#4). The architectural promise that cross-verify outcomes feed routing learnings is therefore a no-op in practice.
- [root-cause|medium] Async interface backed by blocking `spawnSync` — `src/orchestra/monitor-adapter.ts:36` (`const result = spawnSync(cmd, args, { encoding: 'utf-8', timeout: timeoutMs, ... })`) is called from `async` methods declared `Promise<...>` (e.g. `:50` `async listActiveWorkers()`, `:66` `async getResourceUsage()`, `:81` `async killWorker()`). The Promise signatures are cosmetic — every adapter call blocks the event loop, violating ADR-087 (Async I/O & Test Hermeticity) and the karpathy CUSTOM "No spawnSync for subprocesses" rule. The async contract is a false guarantee.
- [root-cause|low] Tmux resource metrics are a hardcoded-null promise — `src/orchestra/monitor-adapter.ts:115` (`async getResourceUsage(_workerId: string): Promise<ResourceUsage | null> { // tmux sessions don't expose resource metrics directly / return null; }`) — the `MonitorAdapter` interface advertises resource metrics but the tmux backend can NEVER provide them; since `'auto'` resolves to tmux (`:205-207`), any consumer of resource usage on the default backend silently always receives `null`.

## Summary
orchestra#14 is dominated by **wired core, dark periphery**: the live model-selection path (`resolveTaskModel` → internal tier helpers) and the live learnings store (`OutcomeTracker` → `.deckent/routing/`) are real and consumed by planner/finalizer/decision-engine, but four sizeable surfaces around them — the `monitor-adapter` module, the `multi-agent` pipeline, the `PatternRecorder/PatternReader` (`.brain/learning/`) subsystem, and `outcome-tracker.recordCrossVerifyVerdict` — are fully built and heavily unit/integration-tested yet have zero production callers. The most consequential softness is the cross-verify learning loop (`recordCrossVerifyVerdict`): documented as an ADR-070 advisory signal but with no producer, so cross-verification never actually influences routing. Secondary structural debt: a duplicate-divergent learning subsystem (pattern-* vs outcome-tracker), an unreachable `premium_plus` tier, and async monitor methods that block on `spawnSync` against ADR-087.
