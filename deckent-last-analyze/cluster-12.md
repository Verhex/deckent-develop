## Findings

- [root-cause|critical] `reconcileRubricNoGo` flips Brain's own NO_GO → DONE using worker-self-reported, unverified `coverage` + `testsPassed` — `src/orchestra/mid-sprint-adapter.ts:662,702,730-733` — `const coverage = typeof result.coverage === 'number' ? result.coverage : 0;` … `if (result.testsPassed === false) { … preserve NO_GO }` … `if (rubricAverage >= RUBRIC_RECONCILIATION_THRESHOLDS.rubricAverage && coverage >= RUBRIC_RECONCILIATION_THRESHOLDS.coverage) { return { decision: 'DONE', reconciled: true, … } }`. Both `result.coverage` and `result.testsPassed` come straight from the worker's own `.result` file — there is no independent re-measurement (no tsc/vitest/git-diff in this pure path). A worker that self-reports `selfAssessment:DONE`, `testsPassed:true`, `coverage:80+` and clears the rubric (avg≥85) overrides Brain's safety NO_GO. This is trust-without-verify: the system's last gate is decided by the actor it is supposed to police. Wired live at `result-evaluator.ts:1259`.

- [unwired|high] 429 provider-failover (`handleRateLimitFailover` / `applyRateLimitFailover`) has zero production callers — `src/orchestra/mid-sprint-adapter.ts:254` and `:81` — `handleRateLimitFailover(task, result, rateLimitState?) { const resolution = applyRateLimitFailover(task, result, rateLimitState); return resolution ? resolution.task : null; }`. Repo-grep: the only callers of either symbol are `tests/orchestra/as2-p3-failover.test.ts`. The live FIX path (`sprint-phases.ts:2047-2055`) does `const { MidSprintAdapter } = await import(...)` + `new MidSprintAdapter(...)` for **reroute** only and never calls `handleRateLimitFailover`. So opus@claude-sub → gpt-5@codex-api equivalent-tier overflow on a 429 never fires at runtime — quota exhaustion in the FIX phase is unhandled. Sub-fault: `is429Error` (`:53-62`) is a free-text substring match (`msg.includes('rate limit')`, `'429'`, …) on worker notes — a note like "no rate limit hit" would false-positive and fabricate the synthetic `RATE_LIMIT_EXHAUSTED_STATE` (`:33-47`); latent only because the whole path is dead.

- [unwired|medium] `loadUserGeneratorsAsync` (MJS executable-generator support) is never wired — `src/orchestra/managed-docs/plugin-loader.ts:72` — `export async function loadUserGeneratorsAsync(projectRoot: string): Promise<SectionGenerator[]> { … await import(fullPath) … }`. Its own docblock (`:70`) says "Not currently wired into the sprint pipeline — reserved for CLI `docs run --with-plugins`." Repo-grep: the only references are the def + comments + `.brain`/`docs/` notes; **zero production caller**, and the `--with-plugins` flag it is reserved for does not exist anywhere in `src/cli/**` (grep `with-plugins` hits only docs/comments, never an `.option('--with-plugins')`). `runManagedDocUpdates` uses the **sync** loader only (`managed-doc-runner.ts:16,31`). The `.mjs` plugin format documented by ADR-030 is therefore permanently inert.

- [unwired|low] `ManagedDocUpdateResult` type + its `sectionsUpdated` field are exported but never constructed or consumed — `src/orchestra/managed-docs/types.ts:71-73` — `export interface ManagedDocUpdateResult extends DocUpdateResult { sectionsUpdated?: string[]; }`, re-exported at `index.ts:4`. Repo-grep for `ManagedDocUpdateResult` returns only its def + the barrel re-export; for `sectionsUpdated` only the def line. `runManagedDocUpdates` returns `DocUpdateResult[]` (`managed-doc-runner.ts:26`), never the extended shape, so `sectionsUpdated` is never populated or read — a dead extension of the result contract.

- [dormant|medium] `ManagedDocEntry.skills` is a documented config knob that no code reads — `src/orchestra/managed-docs/types.ts:17-18` — `/** Skill IDs to reference when generating content */ skills?: string[];`. The runner consumes `entry.path/id/enabled/autoSections/templates/protectedSections/maxLines` (`managed-doc-runner.ts:42-102`) but never `entry.skills`. Grep over `src/orchestra/**` finds no `entry.skills` reader in the managed-docs pipeline. The field is accepted into `.deckent/docs.json` and silently ignored.

- [root-cause|medium] `defaultRunVitestScopeCheck` silently returns a perfect pass when scope maps to no test dir — `src/orchestra/mid-sprint-adapter.ts:409-415` — `const testPatterns = scopeDirs.filter(d => d.startsWith('src/') || d.startsWith('tests/')).map(...); if (testPatterns.length === 0) { return { passRatio: 1, passed: true }; }`. `reconcileSpuriousNoGo` then reads `vitestResult.passed === true` (`:542`) as "vitest PASS" and can flip a NO_GO into GO_WITH_TECH_DEBT (`:555-564`). For any task whose `scope.directories` are not `src/`|`tests/` paths, "no test was run" is laundered into "tests passed" — a silent-fallback that softens the test gate of the spurious-NO_GO reconciler.

- [inconsistent|medium] Duplicate-divergent `resolvePath` — two parallel dot-path resolvers with different semantics — `src/orchestra/managed-docs/template-renderer.ts:95` vs `src/core/condition-evaluator.ts:11` (re-exported via `src/core/index.ts:35`) — `export function resolvePath(scope: unknown, path: string): unknown { … if (current instanceof Map) current = current.get(seg); … }`. The core copy (used for `TaskDNA` condition evaluation) and the managed-docs copy (Map + nested template scope) are independent implementations with divergent Map-handling/null-guard behavior. A fix or hardening (e.g. `__proto__` guard) applied to one will silently miss the other — cross-module drift risk on a name that reads as a single shared util.

- [root-cause|low] `reconcileSpuriousNoGo` "vitest < 50%" NO_GO branch is structurally unreachable in production — `src/orchestra/mid-sprint-adapter.ts:567-578` — `// vitest < 50% pass → NO_GO … notes: \`vitest pass ratio ${...}% < 50% …\``. With the default dep, `defaultRunVitestScopeCheck` can only yield `passRatio ∈ {1 (no patterns), 0 (res.error/non-zero exit), ≥0.5 (json on status 0)}` — a real vitest exits non-zero on any failure (`:424` forces ratio 0), and status-0 implies all-pass (≈1). So `0 < ratio < 0.5` never occurs except via injected test deps; the documented "partial-fail" gate is dead at runtime. Couples with the silent-pass above to make the reconciler's vitest signal effectively binary (1 or 0), not the graded gate its notes claim.

## Summary
This cluster is the managed-docs document pipeline plus the FIX-phase reroute/reconcile adapter, and the two halves fail differently. The managed-docs half is mostly live (`runManagedDocUpdates` is wired at `sprint-docs-updater.ts:118` and into CLI/MCP) but carries accreted dead surface: the `.mjs` executable-generator path (`loadUserGeneratorsAsync`) is permanently unwired with a phantom `--with-plugins` flag, the `ManagedDocUpdateResult.sectionsUpdated` result extension is never constructed, the `ManagedDocEntry.skills` config knob is silently ignored, and a `resolvePath` clone diverges from the core one. The mid-sprint-adapter half is where the consequential root-causes sit: `reconcileRubricNoGo` lets a worker's own unverified `coverage`/`testsPassed` overturn Brain's NO_GO→DONE (trust-without-verify on the final safety gate), the spurious-NO_GO reconciler treats "no test ran" as "tests passed" (silent-fallback) while its graded `<50%` branch is structurally dead, and the entire 429 provider-failover machinery — fully implemented and fully tested — is never invoked in production. The pattern across the cluster: features that are exported, documented, and test-green but either unreachable at runtime or softened to advisory by self-report.
