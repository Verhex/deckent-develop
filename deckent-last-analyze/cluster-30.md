### root-cause
- [root-cause|medium] ADR-014 ".deck is the only secret source" guarantee is documented but not the wired path — `src/core/erp-connector.ts:6-8` — the header asserts `Secret never lands in config.json; the .deck file is the only source` and `buildErpConnectorFromDeck` (`:41-50`) is the function that merges `loadDeckSecrets(projectRoot)` over the env. But because that function is unwired (see unwired finding), the live runtime path is `buildErpConnectorFromConfig(config.erp, process.env)` (`runtime-loop.ts:308`, `process-runtime.ts:44`), which reads credentials from `process.env`/config via `readSecret(cfg, env)` (`erp/factory.ts`). The secret-hygiene invariant the module advertises is therefore soft — nothing on the production path enforces ".deck only."
- [root-cause|medium] Risk-tagged `erp.read` runs ungated in every production path — `src/core/erp-connector.ts:59` (`Tagged medium-risk by work-model.ts`) — the medium-risk approval gate is opt-in default-off (`:82-85` plain install when `gate` absent), and no production caller opts in (`runtime-loop.ts:327`, `process-runtime.ts:54` pass connector with no gate). So a capability the module itself classifies medium-risk dispatches to a real ERP with zero pre-check on the live path; the "approval pattern for erp.read" (`:74`) is a soft, unexercised guarantee. (Same evidence as the dormant finding, framed as the security-guarantee seam.)
- [root-cause|low] Dynamics driver's "defence in depth" re-check is partial — trusts the connector for identifier safety — `src/core/erp/dynamics/driver.ts:188` — the driver re-verifies only `compiled.readOnly !== true || compiled.operation !== 'read'`, but interpolates `predicate.field` and the entity set RAW into the OData URL: `${predicate.field} in (...)` (`:117`), `contains(${predicate.field},...)` (`:125`), `${predicate.field} ${OP_TO_ODATA[...]} ...` (`:127`), and `${serviceRoot}/${entitySet}?...` (`:199`) where `entitySet = opts.entityModelMap?.[compiled.entity] ?? compiled.entity` (`:192`). Field/entity values are never re-validated as safe identifiers here — the driver trusts `ErpConnector.compile`'s allow-list (SSOT note `:32-34`). This holds while every `CompiledQuery` originates from the connector, but `entityModelMap` values are operator-supplied config that the factory forwards UNVALIDATED (`erp/factory.ts:119` `...(cfg.entityModelMap ? { entityModelMap: cfg.entityModelMap } : {})`) — a mapped entity set with URL metacharacters would reach the path raw. Trust-without-(full)-verify by design; the read-only re-check covers the verb but not the identifiers.

## Summary
This cluster is deckent's enterprise read-side, and its honesty is uneven. The ERP query compiler (`erp/connector.ts`) and the Dynamics driver (`erp/dynamics/driver.ts`) are genuinely careful — allow-listed identifiers, mandatory `limit` cap, parameterized values, fail-closed errors, redacted secrets, hermetic injectable `fetch` — and are correctly wired through `erp/factory.ts`. But the safety *wrappers* around them are advertised more strongly than they are wired: `buildErpConnectorFromDeck` (the ADR-014 ".deck-only secret" path) and the entire `installErpHandlerWithApprovalGate` gate branch are dead in production, so the live path reads secrets from `process.env` and dispatches medium-risk `erp.read` with no approval pre-check — two documented guarantees that are soft because nobody opts in. The doc-tracking layer is sound but carries a duplicate-divergent pair (`runDocTrackingSync` vs `runDocsTrackScan`) plus a stale "used by MCP" comment, and `enterprise-config.ts` is a whole stranded F4 module whose only runtime survivor is a single `FlowConfig` type-import — its parse/validate/merge API exists solely to be tested. Net: the primitives are enterprise-grade, but the trust/secret/approval seams are opt-in-and-unwired, which makes the strongest-sounding promises (".deck only", "approval-gated erp.read") the least enforced.
