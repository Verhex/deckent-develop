## Summary
core#4 is the config subsystem's spine and shows a recurring deckent pattern: **breadth of capability that outruns its wiring**. Two whole resolver/guard surfaces (`mergeConfigs`, the v1→v2 tier-migration chain, the chat-provider-fallback pair) and a re-export module (`config-validator.ts`) are fully implemented and green-tested but have zero production call-sites — tests assert behavior on code paths the runtime never executes, which is the most dangerous variety of dead code because coverage looks healthy. The second theme is **documentation/default drift**: `CONFIG_METADATA` (the source for the user-facing config reference) lists five defaults that contradict `createDefaultConfig`, and `condition-evaluator`'s `$exists` operator is undocumented — both are single-file, code-grounded truth-vs-doc gaps. Silent-swallow `catch` blocks in the migration and ci-learning write paths round out the soft-guarantee findings. Nothing here is a correctness bug for a happy-path run, but the unwired duplicates (especially `mergeConfigs`) mean tests over-state real coverage of the live `loadConfig` resolver.
