# deckent Prompt / Scope / Agent-Skill Mechanism — Revamp Analysis

**Date:** 2026-07-08 · **Scope:** worker-prompt token economics (Dimension A) + scope-path validation (Dimension B) + agent/skill selection & evolution (Dimension C) · **Method:** direct source read + live sprint-383 real prompt measurement + git history + spec-doc cross-check. Every claim below is `file:line` or a measured number from real artifacts; anything inferred/uncertain is flagged explicitly.

---

## 0. Executive Summary

deckent already has the **right architecture on paper** for all three dimensions — a tiered T0/T1/T2 prompt-cache design (`prompt-segmentation.ts`), a 5-archetype provider cache adapter (`cache-adapter.ts`), a multi-signal ADR/skill/agent scorer (`adr-selector.ts`, `routing-engine.ts`), and an outcome→promotion feedback loop (`outcome-tracker.ts`, `promotion-pipeline.ts`). The problem is not design — **it is wiring**. Across all three dimensions the pattern repeats: a well-built module exists, is unit-tested, and has **zero real callers** in the sprint-execution path. This is the single unifying finding.

**Headline numbers (measured from real sprint-383 prompts, `.tasks/.prompt-383-*.txt`):**
- A typical worker prompt is **~5,200–5,600 tokens** (chars/4). Of that, **~65%** (skills + agent persona + fully-static boilerplate) is **byte-identical across every task in the same agent+skill class** — yet is re-sent in full, every task, every sprint, on every provider path.
- **Confirmed concrete duplication:** the Karpathy 4-discipline content is injected **up to 4 layers deep** for `refactorer`/`code-reviewer`/`architect`/`doc-writer`/`bug-fixer` tasks (see §3) — one layer (~2.1K tok) is *invisible to deckent's own prompt files* because it is auto-loaded by the Claude CLI itself from `CLAUDE.md`/`.claude/rules/`, so deckent's own measured ~5,200-token prompt **understates** what a Claude-CLI worker actually ingests. **This is verified directly against the installed `claude` binary's own `--help` output (not inferred from a code comment)** — see §3 for the exact flags checked. The same scan also surfaced a ready-made, currently-unused Claude CLI flag (`--exclude-dynamic-system-prompt-sections`) that is Anthropic's own shipped fix for the prefix-instability problem blocking cache sharing on the CLI path (§3, §10 item 1).
- The provider-agnostic prompt-cache machinery to fix this (`prompt-segmentation.ts`'s `computeStablePrefix`/`stablePrefixKey`/`reorderLeadingT0`, and `cache-adapter.ts`'s 5 `ProviderCacheAdapter` archetypes) **exists, is tested, and is imported by nothing outside its own module and its own tests** — confirmed by `grep -rl` returning zero hits in `src/` (see §6). `DEFAULT_LEADING_T0_REORDER = false` and is never flipped from config.
- **Scope validation (Dimension B):** there is no pre-flight check that a `scope.filesWrite` path exists in the repo before a worker is told to write there — confirmed by reading the full scope pipeline (§7), and confirmed **not hypothetical**: sprint-380's orphan-file incident is traceable in git history down to the exact commit (`947473e2`) and the exact still-live archived spawn command (`.tasks/archive/sprint-380/.worker-380-003.sh:102`) that granted `Write()` permission to a path that had never existed. The load-bearing enforcement (the CLI `--allowedTools` allowlist, not just the documented "soft" auditor) is *also* existence-blind — a hallucinated/typo'd path is structurally indistinguishable, at every checkpoint, from a legitimate "create this new file" instruction.
- **Agent/skill evolution (Dimension C):** the routing engine is genuinely multi-signal and the outcome→learning-bonus and outcome→evolved-rule loops are **confirmed live in this exact repo's own data** (`.deckent/routing/learnings.json`, `evolved-rules.json`). But: the specific ADR-075 skill→agent-affinity mechanism is wired-and-reachable yet **permanently switched off** (not simply "dead code" as the project's own memory note implies — a more precise and more actionable distinction); a genuinely dead module (`runIdentityMutation`, zero callers) sits fully-built next to the live promotion pipeline; and a live **data-integrity bug** (unvalidated `forceSkills` overrides) is confirmed actively polluting this project's own outcome stats with phantom 100%-success entries for skills that were never actually injected (§8).

**One coherent story:** deckent already computed the pieces of a self-correcting, cost-efficient, cross-provider prompt/scope/routing system. None of the three feedback loops (cache-tier → provider adapter, scope → existence-check, outcome → routing-weight) closes today. Closing all three is the same shape of fix repeated three times: **wire the existing module into the real sprint-controller/task-builder call path**, not build something new. That is what makes this a coherent "revamp," and why it matters at million-scale: every unwired loop is a cost tax and a quality ceiling that multiplies by tenant count, not just by task count.

## 1. Prompt Assembly Map (Dimension A)

### 1.1 Entry point and pipeline

`src/orchestra/prompt-god-template.ts:259` `buildTaskPrompt(task, ctx)` → delegates to `buildTaskPromptSegmented` (same file) which runs:

`classifyTaskType → selectAgent → selectSkills → selectRelevantAdrs(topN=3, minScore=0.3) → sanitizeScope → renderTemplate (push() calls) → (optional leadingT0Reorder, default OFF) → PromptArtifact`

The renderer builds an ordered array of tagged `PromptSegment`s (`prompt-segmentation.ts:55`) via a sequence of `push(tier, kind, content)` calls. **The actual emission order (verified `grep -n "push("` on `prompt-god-template.ts`, lines 1174–1314) is:**

| # | `push()` call (file:line) | Tier tag | Content |
|---|---|---|---|
| 1 | `:1174` `push('T1','skills', skillBlock)` | T1 | Full `SKILL.md` text of every selected skill |
| 2 | `:1175` `push('T1','persona', agentBlock)` | T1 | Full agent `PROMPT.md` text |
| 3 | `:1176` `push('T1','adr', adrBlock)` | T1 | Selected/tiered ADR text (see §4) |
| 4 | `:1194` `push('T0','worker-contract', ...)` | T0 | "You are a Deckent worker agent..." intro |
| 5 | `:1196` `push('T2','task', ...)` | T2 | Task description + goNogo |
| 6 | `:1206` `push('T2','what-to-do', ...)` | T2 | Fixed 5-step instructions (taskId-templated) |
| 7 | `:1231/:1237` `push('T0','verify-steps', ...)` | T0 | CRITICAL VERIFY STEPS block |
| 8 | `:1260` `push('T0','npm-advisory', NPM_ADVISORY_BLOCK)` | T0 | Dependency-mutation advisory (fully static) |
| 9 | `:1268` `push('T2','scope', scopeBlock)` | T2 | Scope Rules (file lists) |
| 10 | `:1271` `push('T2','deps', ...)` (optional) | T2 | Dependency block |
| 11 | `:1275` `push('T2','heartbeat', ...)` | T2 | Heartbeat format (taskId-templated) |
| 12 | `:1287` `push('T2','result-contract', ...)` | T2 | Result & Self-Assessment format |
| 13 | `:1297` `push('T0','karpathy', KARPATHY_ESSENCE)` | T0 | 4-line Karpathy essence anchor |
| 14–16 | `:1303/:1308/:1314` shared/handoff/comms (optional) | T2 | Worker-comms (COMM-1) blocks |

**Key structural observation:** segments are tagged T0/T1/T2 by *genericity*, but the render order interleaves them for narrative flow, not by tier — `karpathy` (T0) is pushed **last** among the mandatory blocks, after all of the T2 volatile content. `reorderLeadingT0()` (`prompt-segmentation.ts:150`) *can* regroup all T0-then-T1-then-T2 contiguously to maximize a cache-friendly prefix, but it is **only invoked when `ctx.leadingT0Reorder === true`**, and that flag is **never set from any real caller** — confirmed by `grep -n "leadingT0Reorder" src/orchestra/task-builder.ts` returning zero hits. Only `tests/orchestra/prompt-segmentation.test.ts` ever passes it. `DEFAULT_LEADING_T0_REORDER = false` (`prompt-segmentation.ts:115`) is the permanent production behavior.

### 1.2 Where the compiled prompt actually goes (per spawn backend)

`writePromptFile()` (`src/orchestra/tmux.ts:73`) writes the *entire flat compiled string* — segments joined with `\n\n` — to `.tasks/.prompt-<taskId>-<hash>.txt`. This is the file I read directly from a live sprint (`.tasks/.prompt-383-001-0be6f304e1a4e8e9.txt` etc.) — see §2 for exact measured content.

## 3. The 2×–4× Karpathy Duplication — Confirmed, with exact locations

Grepping the real compiled prompts directly (`grep -c -i karpathy .tasks/.prompt-383-*.txt`) shows **2 occurrences for `api-builder` tasks, 3 for `refactorer` tasks** — and a 4th layer exists but is invisible to deckent's own files. In order of where they live:

### Layer 1 — Native Claude-CLI auto-load (invisible to deckent's prompt files; Claude-CLI-only) — **confirmed live against the installed binary, not inferred**
Ran `claude --version` (2.1.204) and `claude --help` directly in this environment. Three flags settle the question definitively:
- `--bare`: *"Minimal mode: skip hooks, LSP, plugin sync, attribution, auto-memory, ... **and CLAUDE.md auto-discovery**."*
- `--safe-mode`: *"Start with all customizations (**CLAUDE.md**, skills, plugins, hooks, MCP servers, custom commands and agents, ...) disabled."*
- `--system-prompt <prompt>` / `--append-system-prompt <prompt>` exist as **replace** / **append** flags for the default system prompt (which is where CLAUDE.md auto-discovery is baked in, per the two flags above — both describe *disabling* it as an opt-out from a default-on behavior).

**None of these flags — `--bare`, `--safe-mode`, `--system-prompt`, `--append-system-prompt` — appear anywhere in `src/orchestra/tmux.ts`, `src/providers/claude.ts`, or `src/providers/subprocess.ts`** (confirmed by direct read of every `buildCommand()`/`buildArgs()` in §6.2's table). deckent's Claude-CLI workers therefore run with Claude Code's **default** system prompt — which means `.claude/rules/karpathy-discipline.md` (119 lines, full 4-discipline document + Quick Reference Checklist + CUSTOM Test-Hermeticity section, **measured ~2.1K tokens** per the project's own code comment), pulled in via `.claude/rules/worker-default.md:51` (`MUST follow @karpathy-discipline.md when generating code.`), **is auto-loaded on every worker spawn**, on top of whatever `writePromptFile()` sends via stdin. **This is not measurable from `.tasks/.prompt-*.txt`** — it happens inside Claude Code's own system-prompt construction, outside deckent's code entirely, and is therefore invisible to deckent's own token accounting (and to `estimatedTokens` fields in task JSON). This is also true of `CLAUDE.md` itself and its full `@`-reference chain (`DIRECTIVES.md`, `.brain/exports/summary.md`, `.deckent/workspace/IDENTITY.md`) plus every other path-scoped `.claude/rules/*.md` file matching the worker's touched paths (`auditor.md`/`brain.md` don't apply to a worker, but `worker-default.md` always does) — **all of it lands in every Claude-CLI worker's context, for free from deckent's point of view, and none of it is currently reduced, deduped, or even measured.**

**A genuinely valuable, ready-made fix surfaced by this same `--help` scan, currently unused:** `--exclude-dynamic-system-prompt-sections` — *"Move per-machine sections (cwd, env info, memory paths, git status) from the system prompt into the first user message. **Improves cross-user prompt-cache reuse.** Only applies with the default system prompt... (default: false)."* This is Anthropic's own, already-shipped fix for **exactly** the prefix-instability problem the project's design spec identifies as blocking real cache sharing on the CLI path (*"git-status snapshot, un-gitignored heartbeat/lock files split the prefix"*) — and deckent passes this flag **nowhere**. Flipping it on for every Claude-CLI spawn is a one-line, zero-risk change (default-off, explicitly opt-in, does nothing when `--system-prompt` is also set) that directly attacks the one blocker §6.2/§9.2 flags as unsolved on the CLI path. This belongs at the top of the fix list (§10).

### Layer 2 — deckent's global essence block (every task, every provider)
`src/orchestra/prompt-god-template.ts:184-188` `KARPATHY_ESSENCE` (4-line, ~95-token distillation), injected once via `push('T0','karpathy', KARPATHY_ESSENCE)` at `prompt-god-template.ts:1297`. The code comment at `prompt-god-template.ts:176-182` **explicitly documents that this is intentionally redundant with Layer 1**: *"Replaces the former full `karpathy-discipline.md` document append (~2.1K tokens/worker): the full depth still reaches Claude workers via the `.claude/rules` project context ... so this short anchor preserves the cognitive effect at a fraction of the token cost."* This is the designed, acknowledged "2×" — a real cost (Layer 1 + Layer 2 both land on every Claude-CLI worker) accepted as a lesser evil than the former full-duplicate design.

### Layer 3 — per-skill "Karpathy Notes" mini-sections (every task, scales with skill count)
Confirmed in the real prompt at line 57: `## Karpathy Notes` inside the `typescript-expert` SKILL.md content itself (3 bullets, ~15–40 tokens depending on skill). This is authored content inside each skill file (e.g. `src/core/builtins/skills/typescript-expert/SKILL.md`), not a code-level injection point — but it means a task with 2–3 skills selected carries 2–3 separate Karpathy-flavored reinforcements on top of Layers 1+2.

### Layer 4 — drifted per-agent "Karpathy 4-Discipline Anchor" (5 of 20 agents only — real duplication bug)
Confirmed via `diff` between `src/core/builtins/agents/refactorer/PROMPT.md` (134 lines, **no** Karpathy section) and the **actually-loaded-at-runtime** `.deckent/agents/refactorer/PROMPT.md` (155 lines) — the workspace copy has an extra **27-line, ~1,868-char (~467-token)** `## Karpathy 4-Discipline Anchor` section (lines 129–155) that does not exist in the `src/core/builtins/` source template. This is the section visible in the real prompt at `.tasks/.prompt-383-003-*.txt:193` (`"## Karpathy 4-Discipline Anchor"`).

`git log --oneline -- .deckent/agents/refactorer/PROMPT.md` shows this was added by commit **`ec91a409 fix(agents): Karpathy-align agent/skill catalog + PCOMP-W5 role signal + W5b secure-coding extraction`** — a past sprint edited the **runtime workspace copies** (`.deckent/agents/*/PROMPT.md`) directly, but **never propagated the change back to the source templates** (`src/core/builtins/agents/*/PROMPT.md`, which are what `deckent init`/sync would use to seed a fresh `.deckent/` workspace). `grep -rl -i karpathy .deckent/agents/*/PROMPT.md` shows exactly **5 of 20 agents** carry this drifted duplicate: `code-reviewer`, `architect`, `doc-writer`, `bug-fixer`, `refactorer`. `grep -rl -i karpathy src/core/builtins/agents/*/PROMPT.md` returns **zero** — confirming zero of the 20 source templates have it.

**Both `.deckent/agents/*/PROMPT.md` and `src/core/builtins/agents/*/PROMPT.md` are git-tracked** (`git ls-files .deckent/agents/refactorer/PROMPT.md` returns the path; not gitignored) — this is not a build artifact, it is a genuine two-copy content-drift bug: the canonical catalog (`src/core/builtins/`) and the live catalog (`.deckent/agents/`) have silently diverged since sprint-191/the `ec91a409` commit, for 5 specific agents.

**Net effect per task, worst case (a `refactorer` task, Claude-CLI worker):** Layer 1 (~2.1K, invisible) + Layer 2 (95 tok) + Layer 3 (1 skill × ~20 tok) + Layer 4 (467 tok) = **~2,700+ tokens of Karpathy-discipline content, 4 separate times, for one task.**

### Fix
1. **Layer 4 (real bug, highest priority):** either (a) delete the drifted Anchor section from the 5 `.deckent/agents/*/PROMPT.md` workspace copies and rely on Layers 1+2+3 (matches the other 15 agents' behavior), or (b) if the anchor's agent-specific rephrasing (e.g. refactorer's "Rule of Three" framing) is judged valuable, **port it back into `src/core/builtins/agents/*/PROMPT.md`** so source and workspace stop drifting, and consider whether Layer 2's generic essence should then be *suppressed* for agents that already carry a bespoke anchor (a `hasOwnKarpathyAnchor` flag on the agent manifest, checked before `push('T0','karpathy', ...)`).
2. **Layer 2 vs Layer 1:** this is a deliberate, documented trade-off already reasoned about in the source comment — leave it, but make the trade-off's cost explicit in cost dashboards (Layer 1's ~2.1K tokens are currently *free lunch* in deckent's own token accounting, i.e. invisible, which understates true Claude-CLI cost — worth a note in `docs/reference/` so nobody "optimizes" Layer 2 to zero assuming Layer 1 alone covers non-Claude providers, since Codex/Gemini/Ollama workers get **no** Layer 1 equivalent at all).
3. **Layer 3:** low-value, low-cost; leave as-is (it's authored per-skill content, and removing it would require touching every SKILL.md).

## 4. ADR Injection Assessment

### Selection mechanism (`src/orchestra/adr-selector.ts`)
Selection is genuinely **multi-signal, not naive-keyword**: `selectRelevantAdrs(task, allAdrs, topN=3)` (`:332`) scores every accepted ADR against the task on five independent axes, summed:
- `scoreScopeMatch` (`:152`) — **+0.4** if the ADR text mentions a specific file the task will write, or a directory ≥3 levels deep (a PCOMP-W3 fix explicitly narrowed this from directory-level matching after it was found to over-match — "every orchestra task scope-matched the Routing ADR" false-positive, per the comment at `:162-167`).
- `scoreKeywordMatch` (`:209`) — up to **+0.3**, requires ≥15% word-overlap between task text and ADR text.
- `scoreIntentPreference` (`:237`) — **+0.2** if the ADR is on a per-intent preference list.
- `scorePresetBonus` (`:252`) — **+0.3** if the ADR is in a per-task-type preset (guarantees architecturally-critical ADRs always surface).
- `scoreAgePenalty` (`:268`) — up to **−0.1** for ADRs >50 sprints old.

`DEFAULT_ADR_MIN_RELEVANCE = 0.3` (`prompt-god-template.ts:222`, mirrored in `config.ts:252`) filters out low scorers; if every candidate falls below threshold, the entire ADR block (header included) is omitted.

### Rendering — tiered, already optimized once (PCOMP-W4)
`buildAdrPromptSection` (`adr-selector.ts:573`) renders differently by **tier** (`classifyInjectionTier`, `:450`):
- **Governing** (the task's ADR is *explicitly referenced* in its own text, e.g. "ADR-D-004") → **full body verbatim**, zero-loss by policy (`:643-655`). This is what produced the full C1–C7 "Contract (binding)" text for `adr-d-004` in the real 383-001 prompt.
- **Constraint** (scoring-selected, not explicitly referenced — the common case) → distilled to a single **"Active constraint:"** line (≤240 chars, `ACTIVE_CONSTRAINT_CAP`, `:674`) + an optional author-marked slice or Contract section + a pointer string `[background constraint — full text: .brain/memory.db adr-xxx]`. This is what produced the one-liner truncation for `adr-g-006`/`adr-g-034` in the real prompt.

The code comment at `:600-601` states this tiering was built specifically to **"remove the measured ~40–50% dead weight (full D-004/G-006 bodies on a CRASH-REDACT task)"** — i.e. this exact waste pattern was already identified and partially fixed in a prior sprint (PCOMP-W4). ADR injection is **not** naive/unconsidered; it is a genuinely-engineered, previously-optimized subsystem.

### What remains a real weakness
1. **The `[full text: .brain/memory.db adr-xxx]` pointer is not actionable by the worker.** Nothing in `worker-default.md` or the generated prompt tells the worker how to dereference it (no `deckent recall` invocation instructed, no sqlite path given as a Bash-queryable target). It is effectively a **human/Brain traceability breadcrumb**, not a worker instruction — real but small (~10–15 tok/ADR) cost with zero functional payoff for the worker itself.
2. **Selection varies per-task even within the same agent** — confirmed directly: 383-001 (api-builder) selected 3 ADRs totaling 785 tok; 383-005 (**same agent**, different task) selected ADRs totaling only 292 tok. This means the ADR block, despite sitting in the nominal "T1" (project/task-class-stable) tier in `prompt-segmentation.ts`, is **actually per-task-varying content** — it would poison any naive cache-prefix keyed at the T1 boundary. `prompt-segmentation.ts:80` classifies `adr: 'T1'` unconditionally; this is optimistic relative to the measured reality.
3. **No compliance-tracking loop exists for the injected ADR text itself.** The only mechanical ADR enforcement found is `authority-enforcer.ts` (ADR-008/ADR-D-004 import-direction check, `core/ → orchestra/` only) — confirmed **advisory/soft** by the real prompt's own ADR block text: *"Active constraint: `authority-enforcer.ts` (ADR-008 check) scans `core/ → orchestra/` only, advisory/soft per ADR-G-020 V1.0 — warns + emits, no hard-block."* For the other ~40 accepted ADRs (routing, native-terminal, dependency policy, etc.), there is no mechanical check of whether a worker's diff actually complied — compliance is trusted entirely to the LLM having read and internalized a one-line distillation, with **no verification loop closing the cost back to a measured value**. `sprint-phases.ts:1785` has an `enforce_adr_compliance` gate flag, but it gates on the *same* narrow authority-enforcer signal, not general ADR adherence.

### Verdict
ADR injection is **relevance-driven and reasonably cost-optimized already** — the "is it generic noise" concern is largely unfounded for the *selection* step. The real gaps are (a) selection isn't deterministic-per-task-class so it can't sit cleanly in a cache-stable tier, and (b) there is zero closed-loop measurement of whether the injected text changes worker behavior — the system cannot currently tell a load-bearing ADR from a decorative one, which matters for §8's pruning proposal.

## 5. Static vs. Dynamic Split

| Section | Genuinely static (global, any task/project) | Stable per (agent, skill-set) task-class | Genuinely per-task-instance |

| Worker-contract intro | ✅ ~33 tok | — | — |
| CRITICAL VERIFY STEPS | ✅ ~556 tok (mode-templated: "targeted" vs "doc-only", 2 fixed variants) | — | — |
| What-To-Do / Heartbeat / Result-contract | Template text is static; **classified T2 anyway** because `task.id` is interpolated into the same string (`prompt-segmentation.ts:68-70` — explicit design note: byte-variance, not semantic role, drives the tier) | — | small taskId substitution |

**Actionable nuance not yet exploited:** the What-To-Do/Heartbeat/Result-contract blocks are ~99% static text with a single `task.id` token substituted in 2–3 places. A trivial refactor — render the fixed template as a genuinely global T0 constant and interpolate `task.id` via a short separate reference line appended *after* a cache breakpoint — would reclassify ~704 tokens (§2 sub-table: 156+121+427) from "T2 volatile" to "T0 global," on top of the ~1,091 already-T0 tokens. That moves the truly-cacheable floor from ~1,091 to **~1,795 tokens of pure T0**, before even touching skills/agent/ADR.

## 6. System-Prompt-Caching Architecture — the pieces already exist, unwired

### 6.3 Proposed wiring (closing the loop that already exists on paper)
1. **Turn on `leadingT0Reorder`** (flip the currently-unused `ctx.leadingT0Reorder` from a config flag, `config.prompt.*`) so the compiled segment order is genuinely T0-then-T1-then-T2 contiguous — a prerequisite for any provider-side breakpoint placement to actually separate "static" from "volatile" cleanly.
2. **Call `computeStablePrefix()` + `stablePrefixKey(tenantId, taskClass)`** from `task-builder.ts` at spawn time, and pass the resulting `SegmentedPrompt {t0, t1, t2}` (already the exact type `cache-adapter.ts:56` expects) into the already-built `ProviderCacheAdapter.emit()` for the active provider. This is a **wiring change, not new logic** — `ExplicitMarkerCacheAdapter.emit()` (native Anthropic API path, once F2-008 lands) already knows how to place ≤2 `cache_control` breakpoints at the T0/T1 boundary and the T1/T2 boundary; `ImplicitAutoCacheAdapter` (Codex/Gemini/OpenAI-compatible-implicit path) already knows how to emit a tenant cache-key; `LocalKvCacheAdapter` (Ollama) already knows to emit `cache_salt`.
3. **For the Claude-CLI spawn path specifically** (today's dominant path per real sprint evidence), the two available levers *without* the native-API migration are: (a) reduce raw bytes sent (§3 fixes + reclassifying What-To-Do/Heartbeat/Result-contract as T0, §5), and (b) stabilize the prefix (gitignore/exclude the files whose presence currently makes each worker's CLAUDE.md-adjacent context snapshot differ) so that *if* Claude Code's own internal caching ever does share across sibling invocations in the same working tree, it isn't defeated by incidental byte drift. Do **not** present this as "enable prompt caching" to the owner as if it closes the loop — it only removes self-inflicted cache-poisoning; real cross-worker sharing on this path remains the closed-negative-result per the design spec.
4. **Wire the Ollama-agentic path's `buildSystemPrompt` up to include skills+agent persona** (currently the leanest of the three paths, deliberately by parity-design per the spec doc's Pillar 1 note — "any invariant guaranteed on path 1 must be guaranteed on path 2, or rules leak on the agentic path") — today it under-injects relative to the CLI path (no skill/agent text at all), which is a correctness/consistency gap in the *opposite* direction from the CLI path's over-injection, and worth resolving in the same pass since both paths are touched.
5. **Route worker spawns through the OpenAI-compatible HTTP adapter's real `messages[]` split** wherever that provider path is actually used (`http-agentic-worker.ts`), so skills+agent+ADR text lands in `role:'system'` and only task-instance content lands in `role:'user'` — this is the one path where "just build the system/user split" is close to a pure win with no regime caveat, because it's a genuine per-token-priced API, not a CLI subscription meter.

## 7. Dimension B — Scope Path Validation

### 7.1 The pipeline, end to end — no existence check anywhere

**Origin.** A task's `scope.filesWrite`/`filesRead` comes from one of two sources, neither of which is grounded against the real file tree at the moment it matters:
- **DIRECTIVES.md regex parsing** — `extractScopeFromDirective()` (`src/orchestra/task-builder.ts:843-943`) pattern-matches `Files:`/`Dosya:`/`Scope:`/`Kapsam:` lines plus catch-all path-shaped tokens. Pure string matching over whatever text was authored; nothing here consults the filesystem.
- **AI planner** — `buildPlanPrompt()` (`src/orchestra/planner.ts:128-260`) *does* include a real-repo grounding signal, `context.projectState.fileTree` (populated by an actual `git ls-files` in `sprint-planner.ts:219-222` — **4,670 tracked files** in this repo). But that grounding is nearly inert in practice: (a) `git ls-files` is lexicographically sorted and the prompt only keeps the **first 100 entries** (`planner.ts:143`) — verified empirically that neither `src/agents/worker.ts` (real position 1,595) nor `src/core/provider.ts` (real position 2,155) appear anywhere near that slice; (b) the file-tree section is injected at **priority 8 of 8** (`planner.ts:165`) inside a **200-line total context budget** (`BRAIN_PLAN_MAX_CONTEXT_LINES`, `core/constants.ts:138`), so it is the first thing truncated to near-zero once the higher-priority DIRECTIVES/MEMORY/DEBT sections eat the budget (a documented, separate bloat problem in this project). The planner's own output validator, `PlannerTaskSchema` (`planner.ts:28-46`), only checks **shape** (`z.array(z.string())`), never content — a syntactically valid but nonexistent path passes cleanly.
- There **is** an existing precedent for exactly this kind of check: `auditPlanGroundTruth()` (`planner.ts:763-804`) already validates *numeric* claims in task text (e.g. "16 agents") against a real `readdirSync` count (`plannerMeasureAgentsCount`, `:719-729`) — the "measure reality, don't trust the LLM's claim" pattern is already accepted practice in this codebase, it has simply never been extended to scope paths.

**Sanitization ≠ existence.** `sanitizeScope()` (`src/orchestra/scope-sanitizer.ts:73-154`) is a genuine security/noise filter — rejects absolute paths, `..` traversal, `dist/` prefixes, extension-only tokens, JS-property-access false positives (`.length`), placeholder names (`foo.ts`), unqualified basenames, protected globals (`package.json`). **It has no `fs` import at all.** It answers "is this string shaped like a safe, real-looking path," never "does this path exist."

**Collision detection ≠ existence.** `scope-collision.ts` (orchestra, `:57-63`) and its Nervous-system duplicate (`nervous/detectors/scope-collision.ts:63-164`) both detect **multiple tasks claiming the same string** — never whether that string resolves to a real file. `scope-collision-rate.ts` is a third layer that just counts collision *rate*, consuming counts, not paths. (Aside: `nervous/runtime-scope-check.ts` is a false lead by name — it's an unrelated ADR-037 RBAC guard, `assertBrainScope()`, nothing to do with file scope.)

**Prompt rendering ≠ existence.** `buildScopeBlock()` (`prompt-god-template.ts:563-619`) calls `sanitizeScope()` only, then renders the same fixed template — *"WRITE authority (canonical — the ONLY files you may create or modify)"* (`:605`) — **identically** whether the path exists or is a planner hallucination. This wording is exactly why a worker "dutifully creates" a wrong-path file: the prompt speaks with total authority about a path that may not correspond to anything real, with zero hedge language available to trigger doubt.

**The real, load-bearing enforcement is also existence-blind — and it's a hard gate, not the soft one CLAUDE.md documents.** `buildAllowedWriteTargets()` (`src/orchestra/sprint-spawner.ts:276-290`) builds `['.tasks/', ...directories, ...filesWrite]` and joins it straight into the Claude Code CLI's own `--allowedTools "Read,Write(path1,path2,...),Edit(...),Bash,Glob,Grep"` flag (`sprint-spawner.ts:633-634,915-916` — confirmed live in the archived wrapper script `.tasks/archive/sprint-380/.worker-380-003.sh:102`). This is a genuine OS/tool-level permission boundary (Claude Code enforces it), but Claude Code's `Write(...)` pattern-matcher treats a nonexistent path exactly like an existing one and happily **permits** creating a new file there — because from the CLI's point of view, granting write permission to a not-yet-existing path is indistinguishable from "please let me create this." Nothing downstream ever signals "this path doesn't currently exist, verify before creating."

The **post-hoc/soft layer** (`checkBoundaryViolations()`/`isFileInScope()`, `monitor/auditor.ts:627-688`, matching the CLAUDE.md gotcha) is existence-blind in the *opposite* direction: it only flags writes **outside** the declared scope list. A write to a listed-but-nonexistent path is, by definition, inside scope — invisible to this layer by construction, not merely uncaught by an oversight. **Neither the hard gate nor the soft audit was ever designed to ask "is the declared scope list itself accurate" — both only ask "did the worker stay inside it."**

### 7.3 New-file vs. typo/hallucination: **zero distinguishability today**

Confirmed by search, not assumption: no fuzzy-matching/Levenshtein/"did-you-mean" logic exists for scope paths anywhere (the one hit for "did you mean" in `src/cli/entry.ts:98` is Commander's own command-name suggestion, unrelated). `TaskScope` (`core/task-types.ts:235-239`) is a flat `{directories, filesRead, filesWrite}` of plain strings — **no per-path metadata slot** even exists to carry an existing/new distinction if one were computed. The rendered "Scope Rules" text is identical regardless. A task description sometimes contains create-vs-modify language ("create a new test file") but this is never structurally consulted by any validation code — it's free text the worker itself has to interpret, unaided.

### 7.4 Proposed self-validating mechanism (analysis)

**The ground truth is already computed and thrown away.** `sprint-planner.ts:219` already runs `git ls-files` into `context.projectState.fileTree` for every plan — it is simply truncated to 100 entries and starved by context-budget priority before the LLM ever meaningfully sees it. The fix is not "prompt the LLM better with more of the file tree" (still probabilistic); it is to **validate the plan's output against the same already-fetched `fileTree` programmatically after the plan returns** — the exact pattern `auditPlanGroundTruth()` already established for numeric claims, extended to paths.

**Proposed `evaluateScopeGate(tasks, fileTree)`**, structurally parallel to the existing pre-spawn cost gate (`core/cost-gate.ts:111`, `evaluateCostGate()`, wired into `deckent_start` and documented as "pre-spawn cost gate active" in the MCP tool description — `COST_GATE_EXCEEDED` unless `acknowledgeCost: true`). Classify every `scope.filesWrite`/`filesRead` entry, across all tasks in a plan, into:
1. **CONFIRMED-EXISTING** — exact match in `fileTree` (or created earlier in the same plan's own dependency chain).
2. **NEW-FILE, plausible** — doesn't exist, but the task description uses create-language and the parent directory already exists with sibling files of the same kind (e.g. a new `tests/orchestra/foo.test.ts` next to other `.test.ts` files).
3. **SUSPECT — likely typo/hallucination** — doesn't exist, AND a fuzzy match exists elsewhere in `fileTree` with the same/near-identical basename in a different directory (a cheap `basename → path[]` index over `fileTree`, no full Levenshtein needed for the common case; a bounded edit-distance pass, threshold ≤2–3, catches genuine misspellings).

Bucket 3 should **block spawn by default** (`SCOPE_GATE_SUSPECT`, naming the suspect path(s) and fuzzy candidates — *"did you mean `src/agents/worker.ts`?"*), overridable via an explicit `acknowledgeScopePaths: true` (MCP) / `--force-scope` (CLI), mirroring the already-familiar cost-gate UX so operators don't learn a new mental model. Bucket 2 shouldn't block, but should change the rendered prompt.

**Prompt-level fix, independent of whether the gate blocks:** `buildScopeBlock()` should render three sub-lists from this classification instead of one flat list — *"CONFIRMED EXISTING — read/modify, do not recreate,"* *"NEW FILES you are expected to create,"* and (only if a suspect override is used) *"⚠ could not be confirmed and no plausible existing file matches — verify before writing; if this should be an existing file, STOP and NO_GO rather than creating a new one."* This directly closes the sprint-380 failure mode: a worker told *"unconfirmed, verify before creating"* has an actionable instruction to stop and flag, instead of the current *"canonical write authority"* wording that gives it every reason to proceed and none to doubt.

**Placement:** a pure decision function in `src/core/` (same layer as `cost-gate.ts`, testable with an injected `existsSync`), wired at two points — (1) immediately after the AI-planner/DIRECTIVES-parser returns tasks, before anything is written to `.tasks/`, and (2) defensively inside `sprint-spawner.ts`'s `buildAllowedWriteTargets()` call site, right before the `--allowedTools` string is assembled, to catch drift from manual task-JSON edits between plan and spawn.

### 8.3 Drift confirmation — the same Karpathy-anchor drift from §3 is *not* an isolated agent-file quirk, it's how the agent-pool always resolves

`agent-pool.ts:getAgentPrompt()` (`:868-944`) resolves in this order: (1) `.deckent/agents/<id>/PROMPT.md` (workspace, **checked first**) → (2) `.tasks/agents/<id>/PROMPT.md` (temp scope) → (2.5) `src/core/builtins/agents/<id>/PROMPT.md` **only if neither of the above has any record at all** → (3) degraded `agent.json::systemPrompt` fallback. Every widely-used built-in agent already has a materialized workspace copy, so **the builtins tree is never actually reached for them** — it only serves brand-new agents with no workspace file yet (confirmed: `api-designer`, `i18n-specialist`, `observability-engineer` exist only under `src/core/builtins/agents/`). This makes the §3 Karpathy-anchor drift structurally guaranteed to be live, not incidental: **whatever is hand-edited into `.deckent/agents/<id>/PROMPT.md` is exactly what ships**, permanently, until someone edits the same file again — `src/core/builtins/` is a seed template, not a source of truth once a workspace copy exists.

End-to-end confirmation this is the real spawn path (not a side function): `result-collector.ts:resolveAgentPrompt()` (`:668-675`) calls `getAgentPrompt()` and is called from `sprint-spawner.ts:628,911` and `cli/commands/spawn.ts:215`, feeding straight into `task-builder.ts:buildWorkerPrompt()` (`:1567-1638`) → `buildTaskPrompt()` → the actual `.prompt-*.txt` file executed by the worker.

**A live data-integrity bug found while verifying real numbers, relevant to both C and the cost picture:** `resolved.forceSkills` (`routing-engine.ts:574-583`, a Brain-directive override) flows straight into `task.assignedSkills` with **no skill-pool existence check**. ### 8.5 Token-cost vs. selection — real numbers, and the pruning gap

Real task (`task-383-002.json`): `estimatedTokens: 5205`, agent `api-builder`. `api-builder/PROMPT.md` ≈ 739 words (~950–1,000 tok); `typescript-expert/SKILL.md` ≈ 603 words (~800 tok) — together roughly a third of the total, consistent with §2's measured breakdown. Agent `PROMPT.md` sizes across the workspace range 174–1,283 words; skill `SKILL.md` sizes range 603–1,067 words. Typical skill count per real task: 2–3, matching `calculateSkillBudget`'s small/medium-task default cap of 3 (`routing-engine.ts:1240-1273`).

**No mechanism tracks which skill *sections* influenced an outcome, and no pruning mechanism exists at all.** The closest analog, `adaptive-agent.ts:adaptAgentRuntime()`/`SkillAdaptation` (`:244-297`, invoked from `outcome-tracker.ts:generateSkillAdaptation()` on every `recordOutcome()`), is coarse and **one-directional**: it maps whole-agent weakness patterns to a suggestion to **add** a skill; `suggestRemove` is **hardcoded to always return `[]`** (`:295`) — there is no code path that ever proposes removing a skill, let alone pruning part of one, and the suggestion only reaches a retro doc as advisory text, never auto-applied to routing.

There is one real, live, already-wired relevance filter on already-selected whole skill blocks: `filterSkillPromptsByDNA` (`prompt-token-optimizer.ts:116-153`, called unconditionally from `task-builder.ts:1579-1581` inside the confirmed production `buildWorkerPrompt` path) scores each selected skill's name + first-200-chars against intent/domain keywords and drops a whole skill block below threshold (with a safe all-zero fallback that keeps everything). This is real cost-reduction machinery already running in production — but it is a **static keyword heuristic**, not outcome-data-driven, and it operates on whole skill blocks already inside the 2–3 budget, not on sub-sections of a skill's content.

### 8.6 Proposed live-evolving + cost-reducing design (analysis)

1. **Fix the phantom-skill-ID bug first (8.4).** Validate `resolved.forceSkills` against the real skill pool at routing time (`routing-engine.ts:574-583`) and reject/warn on unknown IDs before they pollute `learnings.json`. Every downstream evolved-rule/promotion decision is only as trustworthy as this input, and it is confirmed polluted today.
2. **Wire `computeStablePrefix`/`stablePrefixKey` into the real build path** — this is the same fix as §6.3, restated from the routing side: derive a `taskClass` key from `(assignedAgent, sorted(assignedSkills), taskDNA.domains)`, and route the resulting T0+T1 segment (persona + skills + Karpathy + ADRs) through whichever provider cache is active once wired, leaving only the T2 tail per-task. This project's own `learnings.json`/synergy data already shows heavy task-class recurrence (e.g. `testing-expert` co-occurring with `typescript-expert` in 221 samples) — exactly the repetition a task-class cache key would exploit.
3. **Extend the already-live, confidence-scored `evolveRules()` auto-apply gate to a skill-content-pruning verdict**, not just activation rules — but only after adding a section-level attribution instrument first (a cheap diff between a skill's H2 headings and what the worker's own tool-calls/result notes actually touched), specifically to avoid pruning a rarely-triggered-but-critical section (e.g. a security caveat) that looks "unused" in aggregate but matters the one time it fires.
4. **Turn `runIdentityMutation` from dead code into a real consumer of the already-live promotion/demotion data** — wire it into `sprint-finalizer.ts` right after `pipeline.evaluateDemotions()` (`:1326`) so a demoted agent gets a proposed mutated variant instead of the current dead end (demotion today just disables; nothing proposes a replacement). This is fully built and tested — the gap is purely a missing call site, identical in shape to the cache-adapter and stable-prefix findings.

## 9. Quantified Cost + Quality Win

### 9.1 Raw token waste (regime-independent — true in every billing model, today, with zero new infrastructure)
- **Layer-4 Karpathy drift** (§3): ~467 tokens/task removed for the 5 affected agents (`code-reviewer`, `architect`, `doc-writer`, `bug-fixer`, `refactorer`) — on a ~5,600-token `refactorer` prompt, that's **~8.3% of that task's prompt, for free, by deleting a drifted duplicate block.**
- **ADR pointer boilerplate** (§4): ~10–15 tok/ADR × up to 3 ADRs ≈ 30–45 tok/task — small but non-zero, and easy to strip if the pointer is judged non-actionable.
- **Combined, conservative:** **~5–9% raw token reduction per task**, concentrated on the 5 drifted agents, achievable with a single-file diff + a decision on whether to preserve the agent-specific rephrasing (§3 fix option (b)).

### 9.2 Caching-recoverable tokens (regime-split — do NOT collapse into one number)
Per task-class recurrence (measured: `api-builder`+`typescript-expert` and `refactorer`+`typescript-expert` each recurred 4× in an 8-task sprint), the **class-invariant** portion is skills (1,016) + agent (1,279–1,656) + fully-static boilerplate (1,091, or ~1,795 after the §5 What-To-Do/Heartbeat/Result-contract reclassification) ≈ **3,386–4,467 tokens per task-class**.

- **$-per-token API regime (native Anthropic API / OpenAI-compatible gateways), once wired:** for a task-class repeated *n* times in a sprint, the first occurrence pays a cache-write premium (Anthropic: 1.25×–2×; most `IMPLICIT-AUTO` providers: free), every subsequent occurrence pays a **cache-read** rate (Anthropic: ~0.1×; provider-typical: 0.1×–0.5×). For a sprint of ~14 tasks with 2 recurring 4× classes at ~3,400 static tokens each: **~3× repeats × 3,400 tok × (1 − 0.1) ≈ 9,180 "avoided full-price tokens" per class per sprint**, roughly **18,000+ tokens/sprint** across the two classes shown — this is a **real, achievable** number *once the native-API path lands and the adapters are wired* (§6.3 items 1–2).
- **Claude-CLI subscription regime (today's dominant path):** per the design spec's own closed-negative-result, cross-worker sharing does **not** happen here — so the ~3,386–4,467 static tokens are paid as a fresh `cacheWrite` (1.25× weight) on **every single spawn**, not just the first. The only lever available without the native-API migration is the raw-byte reduction (§9.1) plus reclassifying the What-To-Do/Heartbeat/Result-contract templates as truly-static (§5), which shrinks what gets rewritten every time — it does **not** convert repeat spawns from write to read. State this to the owner as: *"on the CLI path, shrinking static content is the only lever; enabling caching there does not by itself produce a saving until the prefix-instability root cause is fixed AND/OR the native-API path replaces CLI spawn."*

### 9.3 Correctness and reliability gain (Dimensions B + C, not token-cost but directly cost-adjacent)
- **A single sprint-380-class incident is expensive in a way tokens don't capture:** an orphan file created at a hallucinated path required a dedicated cleanup sprint, left two permanent re-export shims still imported by real tests today (`tests/orchestra/worker-approval-gate-wire.test.ts:16`, `tests/providers/cred-scrub-all-adapters.test.ts:67`), and recurred in the same commit family as a separate git-self-mutation incident (`947473e2`'s own message: "born-499 self-mutation NÜKSETTİ"). A `SCOPE_GATE_SUSPECT` pre-flight check (§7.4) is cheap (reuses data already fetched by the planner) relative to the cost of one more such incident at million-tenant scale, where a single mis-scoped task multiplies into thousands of orphan-file risks across concurrent tenants.
- **The phantom-skill-ID bug (§8.4) is quietly corrupting the exact outcome data that the whole routing-evolution story depends on being trustworthy.** `security-auditor` (11 tasks/100% success) and `testing` (31 tasks/100% success) are phantom entries in this repo's real `learnings.json` — above the `MIN_SAMPLES=5` floor used to gate rule auto-application. Any dashboard, retro report, or future auto-promotion decision that trusts per-skill success rates today is trusting numbers with confirmed contamination. This is a data-quality fix, not a token fix, but it is a prerequisite for every item in §8.6 and for the caching-by-task-class proposal in §6.3/§8.6 item 2 (a task-class key built from a corrupted `assignedSkills` list is unreliable).

### 9.4 Quality gain (independent of token cost)
A ~5,200-token single flattened user-turn blob (skills → agent → ADR → boilerplate → task, in that order) puts the actual task description **roughly in the middle** of the prompt — a well-documented "lost in the middle" risk for long single-turn contexts. Moving the static ~65% into a genuine system-prompt/cached-prefix channel and leaving a **short, front-loaded, task-only user turn** (task description + scope + goNogo + idempotency key, roughly 250–350 tokens per §2) means the model's *last-read, highest-attention* content is exactly the task-specific instructions — a cleaner, more task-focused prompt shape independent of any cost saving. This is the "quality gain" half of the owner's ask, and it is achievable even where §9.2's token saving is regime-blocked (i.e. it's worth doing on the Claude-CLI path too, purely for prompt-shape reasons, even though it won't show up as a cache-read line item there).
