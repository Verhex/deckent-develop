---

## 1. Overview

Memory V2 made `.brain/memory.db` (SQLite) the single source of truth for all
project knowledge — ADRs, sprint logs, retrospectives, learnings, tech debt,
violation patterns and project identity. The legacy `.brain/` root `.md`
writers were fully decommissioned (Task #4 + B6–B14).

`.brain/exports/` holds **generated, read-only views** of the DB. Today it
emits only **four** files: `summary.md`, `decisions.md`, `memory.md`,
`debt.md`. This document specifies extending that export so `exports/`
becomes the **complete** human- and LLM-readable mirror of the DB.

This is a **spec for a future sprint**, not an immediate change.

---

## 2. Motivation

Two concerns, both raised during the B6–B14 closeout:

### 2.1 LLM agents may not write SQL reliably

Brain, Worker and Auditor are LLM-driven. They reach `memory.db` through the
`MemoryStore` TypeScript API (`getByType`, `searchMemory`, …) — never raw
SQL — so the *normal* path is safe. The gap is the **out-of-band** case: an
agent that needs to inspect project memory *without* going through compiled
code (e.g. a prompt that says "read the project's past retros"). A SQLite
file is opaque to an LLM; a `.md` file is not. A complete `exports/` set is
the LLM-friendly fallback for every entry type, not just four.

### 2.2 The DB backend is a user choice

`memory.backend` is configurable. If a user moves off SQLite (Postgres, or a
DB-less mode), the `.md` exports are the **portable, backend-independent**
representation of accumulated knowledge. A partial export (4 of ~8 entry
types) means a backend migration silently loses retros, sprint logs,
patterns and identity history.

## 4. Design

### 4.1 `runFullMemoryExport`

Extend the export set so every queryable entry type has a generated view.
New exporters in `core/memory-export.ts`:

- `exportRetroMd(store)` → `exports/retro.md` — latest N sprints' retros
  (full retro content lives in the DB; the export is a bounded window).
- `exportSprintsMd(store)` → `exports/sprints.md` — one row per `sprint`
  entry (metrics at-a-glance), newest first.
- `exportPatternsMd(store)` → `exports/patterns.md` — violation patterns
  grouped by type, with per-sprint occurrence counts.
- `exportIdentityMd(store)` → `exports/identity.md` — the `identity` entry
  content (mirror of `.deckent/workspace/IDENTITY.md`).

Relations: either a dedicated `exports/relations.md`, or inline cross-link
sections within the per-type files (open question — §10).

`runMemoryExport()` becomes data-driven: iterate a registry of
`{ name, fn }` exporters instead of a hard-coded list of four.

### 4.2 Invariants (non-negotiable)

1. **One-directional.** DB → `.md` only. Nothing ever parses `exports/*.md`
   back into the DB. B6–B14 removed the multi-writer hazard; this spec must
   not reintroduce it.
2. **Read-only.** Export files carry a generated-file header
   (`<!-- AUTO-GENERATED from memory.db — do not edit -->`).
3. **Idempotent & deterministic.** Same DB state → byte-identical export
   (stable ordering), so git diffs are meaningful.
4. **Fail-safe.** A single exporter failure must not abort the others or the
   sprint finalize (current `runMemoryExport` already isolates per-exporter).

### 4.3 Regeneration

Regenerated by `runMemoryExport` in the post-finalize hook chain (Step 1),
exactly as today — no new trigger. `deckent memory export` CLI also invokes
the full set.

---

## 5. Size & Decay Bounds

The DB grows unbounded across sprints; exports must not. Per-file bounds:

- `retro.md` — last **N** sprints only (N configurable, default ~10). Older
  retros stay in the DB, reachable via `deckent retro --sprint <id>`.
- `sprints.md` — one compact row per sprint; cheap, can be full history.
- `patterns.md` — active patterns + a bounded recent-resolved tail.
- `identity.md` — single entry, tiny.
- `memory.md` / `debt.md` — already bounded by decay.

The DB remains the complete archive; exports are a **working-set window**.

---

## 6. Trade-offs

| Benefit | Cost |
|---------|------|
| LLM-readable fallback for every entry type | +4–5 git-tracked files in `exports/` |
| Backend-portable knowledge snapshot | Slightly larger finalize step |
| Better `git diff` reviewability of memory changes | Export-format churn must be managed (stable ordering) |
| `deckent doctor` can validate DB↔export parity | Decay/window tuning per file |

The costs are small and bounded; the benefits directly answer §2.

---

## 7. Non-Goals

- **No 2-way sync.** Exports are never an input.
- **No replacement of the DB.** SQLite stays the source of truth; exports
  are views.
- **No entry-history export.** `entry_history` is an audit-trail concern,
  not working knowledge — out of scope here.
- **Not a backend-migration tool.** This spec makes the *data* portable; an
  actual SQLite→Postgres migrator is a separate effort.

## 8. Implementation Plan (for the implementing sprint)

1. **Phase 1 — exporters.** Add `exportRetroMd` / `exportSprintsMd` /
   `exportPatternsMd` / `exportIdentityMd` to `memory-export.ts`, each with
   unit tests (TDD, real temp DB).
2. **Phase 2 — registry.** Make `runMemoryExport` registry-driven; wire the
   new exporters; bound `retro.md` by sprint window.
3. **Phase 3 — consumers.** `deckent doctor` DB↔export parity check;
   `api/server` may serve the new views.
4. **Phase 4 — docs.** Update `docs/reference/api-surface.md` (`.brain/`
   file formats) and the Memory V2 sections of DECKENT.md / CLAUDE.md.
5. Create the ADR once the design is ratified.

---

## 9. Verification

- Each exporter: TDD with a real temp `memory.db` seeded per entry type.
- Determinism test: export twice → byte-identical.
- One-directional test: confirm no module imports an `exports/*.md` parser.
- Window test: `retro.md` capped at N sprints while the DB keeps all.

## 10. Open Questions (for the implementing sprint)

1. **Relations** — dedicated `exports/relations.md`, or inline cross-link
   sections in each per-type file?
2. **`retro.md` window size** — fixed default, or driven by the existing
   memory budget config?
3. **Naming** — `sprints.md` vs `sprint-log.md`; align with `.brain/sprints/`
   per-sprint log files (which still exist as separate artifacts).
4. **`summary.md` overlap** — `summary.md` already surfaces ADRs, learnings,
   patterns at a glance; ensure the new per-type files complement rather
   than duplicate it.
5. **Backend abstraction** — should the exporters read through a
   backend-neutral interface now, anticipating the non-SQLite case?
