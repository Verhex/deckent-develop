## 484-Saga: the EVALUATE-Truncation Defect (Sprints 365–367)

### Apparent vs. real

| Sprint | Aggregator's summary reads | What actually happened (disk-verified) |
|---|---|---|
| 365 | 1 DONE, 8 "pending" — closed as "1/1 DONE" | **9/9** tasks produced a real `.result` file with a genuine self-assessment: 8 self-declared `DONE`, 1 `GO_WITH_TECH_DEBT` (`.brain/archive/sprint-365-tasks/task-365-00{1..9}.result`) |
| 366 | 0 DONE, 8 "pending" — closed as "0/0 DONE" | **8/8** tasks produced a real `.result` file: 7 self-declared `DONE`, 1 `GO_WITH_TECH_DEBT` (`.brain/archive/sprint-366-tasks/task-366-00{1..8}.result`) |

Only `task-365-001.result` (a carryover debt-fix, `fixForTaskId: 362-001-fix`) actually received a `brainEvaluation` (`DONE`) in 365; nothing in 366 did. Every other task in both sprints sat with `task.json.status` frozen at `EXECUTING` (365-002..009) or `PENDING` (365-009 specifically) — Brain's EVALUATE phase never reached them, so `series-metrics.mjs`'s `outcomeOf()` fell back to that stale `task.json.status`, which is not one of the three concrete outcomes, hence "pending." Work was never lost; it was never *counted*.

### Three hypotheses, then the real root cause

The series carries an honest trail of wrong-then-righter explanations, each written down as it was current:

1. **born-483** (`docs/MASTER-PLAN.md` row 483, commit `73295c10`, 2026-07-03) — the 365-live-case, first read as: plan wrote 9 tasks correctly ("Task count: 9" + correct model distribution) but *start* appeared to run only 1 (the auto-debt carryover); 8 tasks looked like they went to archive without ever running, and the sprint closed "1/1 DONE" with no visible loss. Suspected cause at the time: a partial `DRAFT→PENDING` confirm transition, or `start` reading stale sprint-state.
2. **born-484** (`docs/MASTER-PLAN.md` row 484, commit `0d2cf4da`, 2026-07-03) — the 366-live-case, described as "483's bigger sibling": the coordinator saw `sprint.tasks` as empty and closed clean in 4.5 minutes as "0/0 DONE" — but the *spawn* step had in fact seen and launched 8 detached workers (CODEX-V6 included), which ran to completion and wrote their results after the coordinator had already exited; `cleanup` archived them anyway. A same-day forensic follow-up (commit `c1872454`) refined this further: launch logs showed the coordinator *did* see "Task count: 8" and did spawn — so the break was **after** spawn, in EXECUTE/EVALUATE accounting, not before it — and separately flagged that 365's case might be a *different* mechanism entirely (`plan` and `start` launched in the same background `&`-chain racing each other).
3. **The real root cause — commit `14f0a244`** (2026-07-05, `fix(evaluate): born-484 kök-neden`) — a repro-first investigation found neither of the above was the actual mechanism. The first real Codex-CLI results in this window wrote `notes` as a **string array** instead of a string. `result-evaluator.ts`'s `isVerificationTask` path calls `(notes ?? '').toLowerCase()` — on an array, that throws a `TypeError`. The rubric evaluation call had no per-task `try/catch`, so the exception propagated to the sprint's outer catch, which only logged silently to the dashboard and **aborted the EVALUATE loop for the rest of the sprint**. This single defect retroactively explains both 483 and 484 as the *same bug*, viewed from two different task orderings — nothing was ever un-dispatched or lost at spawn/schedule time; the earlier scheduling/race hypotheses were reasonable given what was visible at the time, but incomplete.

**Disk-verified smoking gun**, confirming layer 3 directly rather than by inference:
- `.brain/archive/sprint-365-tasks/task-365-002.result` — task **CODEX-V6**, `provider: "codex"`, `notes` is a JSON array (`["docImpact: none", "No source code, dependency, or lockfile changes made.", ...]`). This was the *second* task Brain attempted to evaluate in 365 (365-001, the carryover fix, went first and evaluated cleanly) — hence 365 closed "1/1," not "0/0."
- `.brain/archive/sprint-366-tasks/task-366-001.result` — the same **CODEX-V6** task, `provider: "codex"`, `notes` again a JSON array. In 366 this was the *first* task Brain attempted to evaluate — hence the loop aborted before stamping anything, closing "0/0."
- `.brain/archive/sprint-366-tasks/task-366-002.result` and `-003.result` — both `provider: "claude"`, both plain-string `notes` — unaffected, and both still show `brainEvaluation: undefined`, because the loop had already aborted on 366-001 before reaching them. This confirms the defect's severity (an aborted *loop*, not a single skipped task) independent of the array-notes root cause itself.

### The fix — commit `14f0a244` (2026-07-05)

Four layers, landed together:
1. **`coerceNotesToString` + `normalizeTaskResultShape`** (`task-result-schema`) — normalizes all 14 `readJsonSafe<TaskResult>` call sites at the disk-read boundary. Deliberately a normalize, not a reject: the underlying work was real, only the shape had drifted; a strict `TaskResultV1` gate is called out as a separate, later step.
2. **Per-task rubric-call armor** — a fault during one task's evaluation now falls back honestly (a worker's own `NO_GO` still stands; anything else caps at `GO_WITH_TECH_DEBT`, never a fabricated `DONE`) and emits a `BRAIN→AUDITOR:EVALUATION_FAULT` event instead of throwing.
3. **A loud outer catch** — stderr + notify + an `EVALUATE_ABORTED` event + a `sprint.evaluateAborted` flag, described in the commit message as "born-453's EXECUTE-surface, EVALUATE's sibling" (i.e. the EXECUTE phase already had this kind of loud-failure discipline; EVALUATE now matches it).
4. **An honest denominator** — `calculateMetrics.totalTasks = max(sprint.tasks.length, evaluations.size)`, so a truncated loop reports e.g. "0/8," never the misleading "0/0."

28 new tests landed with it (notes-normalization + evaluate-loop-armor + metrics-484 families), plus the evaluator/phases/collector suites green and `tsc`/dashboard clean per the commit message. `born-483` is folded into the same root cause (confirmed the same bug, not a separate scheduling defect); `born-485` and `born-486` are unrelated findings surfaced in the same sprint window (see sprint-367 below).

### Source-side prevention — task 367-003 (`RESULT-SHAPE-SOURCE-GUARD`)

`14f0a244` closes the defect on the *consumer* side (Brain's read path). Sprint-367's task 367-003 closes it on the *source* side: it edited the single shared worker-prompt result-contract segment (`src/orchestra/prompt-god-template.ts`, `renderSegments()`'s `T2`/result-contract block — confirmed via `task-builder.ts`'s `buildWorkerPrompt → buildTaskPrompt → buildTaskPromptSegmented → renderSegments` call chain to be the *one* code path shared by every provider, with no per-provider duplicate) to state explicitly: `notes` must be a single string (array/object forbidden, use `\n` for multi-line), `selfAssessment` exactly one of the three literal strings, `filesChanged` an array of path strings. A new test (`tests/orchestra/prompt-result-shape.test.ts`, 4 cases) asserts the guard text renders identically for the claude/codex/gemini provider paths, proving the shared-path claim rather than just asserting it in prose.
